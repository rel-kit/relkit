Add a Users database to an existing RELKIT app using the executable data-model example. You will define
tables, generate migrations, add a custom query and an override, and use the generated CRUD schemas
in a member-registration transaction. You will expose a read operation and verify the result.

<Callout type="note" title="Before you begin" icon="clipboard-check">
  You'll need an existing RELKIT application, Bun 1.3.10 or later, and a new local SQLite database.
  The final test verifies that registration writes both records and rolls back on failure.
</Callout>

Use an installed app with the standard `@app/*` alias. If needed, follow [Create an app](/docs/learn/create-an-app).
If a database service already exists, extend it instead of adding a second one. Preserve existing schema,
environment fields, public service members, and routes.

<Steps>
<Step icon="database">

## 1. Scaffold the database baseline [#scaffold-the-database-baseline]

From an existing application root, the CLI can create the Drizzle service, dialect-specific `items`
table, migration configuration, environment contract, ignore rules, dependencies, and database scripts:

```sh
bun run relkit add database --orm drizzle --dialect sqlite
```

Use `postgresql` or `mysql` for the other Bun-native Drizzle clients. The command installs packages and
runs `relkit check`, but deliberately does not create or apply a migration. Run the reported
`db:generate` and `db:migrate` next steps only after reviewing the schema and setting `DATABASE_PATH` or
`DATABASE_URL`. To follow the richer Users tutorial below, replace the generated `items` placeholder with
the shown Users and Memberships schema instead of adding a second database service.

The scaffold also registers the application-owned Drizzle declaration patch. If you selected
`--no-install`, run `bun install` and `bun run check` before continuing. A skipped installation
has not verified the project. The separate [manual setup](/docs/modules/database/define) is for apps
where you are creating the service yourself; it is not an extra prerequisite after this scaffold.

SQLite is the headless default and uses `bun:sqlite`; PostgreSQL and MySQL use
`drizzle-orm/bun-sql`. `--orm` accepts only `drizzle`. Database is a singleton under
the detected service root: `src/services/database` in grouped apps or `src/database` in existing flat
apps. `--service` and `--create-service` do not select its location.

For every scaffolding flag, see the [CLI reference](/docs/api/cli).

</Step>

## 5. Generate and apply the initial migration [#generate-and-apply-the-initial-migration]

The scaffold installed the compatible Drizzle Kit version. Add this configuration:

<include source="examples/data-model/drizzle.config.ts" lang="ts" meta='title="drizzle.config.ts"'>
  /_snippets/source/examples/data-model/drizzle.config.ts
</include>

From your application's root, generate the migration from the table definitions and apply it:

```sh
export DATABASE_PATH=./data-model.sqlite
bun --bun drizzle-kit generate --name=initial
bun run relkit db migrate
```

Review the generated migration before applying it. In the repository example, the initial migration
already exists, so set `DATABASE_PATH` and run `bun run db:migrate` instead of creating another one.
Keep this environment value for the server, and commit generated SQL and required metadata under
`src/services/database/migrations` with the schema. The installed command owns execution;
scaffolding and service startup do not apply SQL.

Run the compiler now so the database context is available to the next function:

```sh
bun run check
```

## 8. Verify database behavior [#verify-database-behavior]

Create `tests/registration.test.ts`. It uses a separate in-memory SQLite database and the migrations
you generated above. The second case makes membership creation fail after its insert, then checks
that the transaction removes both writes. Your application's database is untouched.

<include
  source="examples/data-model/tests/registration.test.ts"
  lang="ts"
  meta='title="tests/registration.test.ts"'
>
  /_snippets/source/examples/data-model/tests/registration.test.ts
</include>

From your application root:

```sh
bun test tests/registration.test.ts
bun run check
bun run typecheck
export DATABASE_PATH=./data-model.sqlite
bun run dev
```

Tests use an independent in-memory connection; they do not seed the running server. In a second
terminal, query the migrated application:

```sh
curl http://localhost:3000/users\?domain=example.com
```

Use the actual backend port if different. An empty, migrated database returns HTTP `200`
with `[]`. If you also complete the separate [Inspector setup](/docs/modules/operations/inspector),
you can invoke `registerMember` (function ID `users.register-member`) with
`{ "email": "member@example.com", "organizationId": "demo" }`, then repeat the request. Expect a row
containing that email, its generated numeric ID, and `active: true`. Use a different email for another
registration; email uniqueness is enforced by the database.

Inspect the checked `database` service and Users function in the Inspector, normally at
`http://localhost:3210`, and inspect `.relkit/generated/context-registry.d.ts` for the typed table methods.
The `listUsers` function is also directly invokable from the Inspector with `{ "domain": "example.com" }`.

Before deployment, add application-specific authorization, bounded queries, driver configuration,
and tested backup and migration procedures. Continue with [Integrate Better Auth](/docs/modules/database/better-auth)
to plan authentication tables and session wiring.
