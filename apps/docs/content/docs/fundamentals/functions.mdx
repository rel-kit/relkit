A RELKIT function is the reusable unit of application behavior. It owns input, output, declared errors,
managed dependencies, and a handler. Routes, jobs, events, tools, and agents target the descriptor rather
than copying the handler, so every transport uses the same validation and invocation semantics.

The handler receives already validated input. Its returned value is validated against `output`. Publishing
the event is authorized by `dependencies`; importing the event descriptor alone does not grant a runtime
client.

## Invoke another function

The example calls `priceOrder.invoke(...)`, not `priceOrder.handler(...)`. `invoke` enters the common engine
and preserves validation, trace/causation relationships, deadlines, cancellation, service policy, and child
call telemetry.

Calling a handler directly bypasses those guarantees and is unsupported. A nested function call does not
need a managed dependency declaration because the target is an in-process descriptor; resources used by
either function still require their own declarations.

## Build one complete operation

<Steps>
  <Step>
    ### Define the contract first

    Create the input and output schemas close to the function or in a shared domain schema module when more
    than one descriptor owns the contract.

  </Step>
  <Step>
    ### Add declared errors and dependencies

    List only expected domain failures and only the managed clients the handler uses. This produces explicit
    graph edges and a narrow context type.

  </Step>
  <Step>
    ### Implement the handler

    Keep transport parsing out of the function. Accept domain values, use context clients, honor cancellation,
    and return the declared output. Let unexpected defects propagate to RELKIT's safe boundary.

## Hooks and transport policy

`onBefore` transforms validated input before the handler. `onAfter` transforms successful output before
final output validation. Use them for function policy that must apply to every invocation transport. They do
not run as error recovery, and `onAfter` does not run after failure.

Use HTTP middleware for cookies, headers, request-native authorization, or an early `Response`. Use service
middleware for policy shared by a group of functions. Keeping those boundaries explicit makes direct and
asynchronous invocation predictable.
