For the complete architecture and learning path, start with [Service](/docs/service),
[domain design](/docs/service/domains), and [where to put your code](/docs/service/organization).

Every top-level application domain below `src/` contains one `service.ts`; `routes` and `platform`
are separate layers, not domains.
The service is the domain's public boundary: listed functions and events are public;
other descriptors remain internal.

## Define a domain

<include cwd lang="ts" meta='title="examples/commerce/src/orders/service.ts"'>
  ../../examples/commerce/src/orders/service.ts
</include>

Public functions are ordinary callable functions, not event-only subscribers. Members are the original
descriptors, so `orders.createOrder` has the same identity,
schemas, errors, and `.invoke()` behavior as the imported `createOrder` value. Services
do not clone members and do not add `.functions` or `.events` namespaces.

Keep each function, event, error, tool, or agent in its own file below the domain.
`service.ts` should only assemble the public boundary; it should not grow into a file
containing every handler.

## Use a service from routes

<include cwd lang="ts" meta='title="examples/commerce/src/routes/orders/route.ts"'>
  ../../examples/commerce/src/routes/orders/route.ts
</include>

`defineServiceRoutes` restricts each route entry to a public function member and
returns the same immutable route descriptors as `defineRoute`. Request mapping,
middleware, authentication, and response policy remain transport concerns under
`src/routes`.

<Steps>
  <Step>
    ### Define focused artifacts

    Keep functions and events in their own domain files with their own contracts
    and tests.

  </Step>
  <Step>
    ### Assemble the public boundary

    List only the functions and events that other domains or routes may use.

  </Step>
  <Step>
    ### Map transport explicitly

    Import the service from route files and map methods with
    `defineServiceRoutes` or `defineRoute`.

  </Step>
</Steps>

## Cross-domain dependencies

Import another domain's `service.ts` with ordinary TypeScript imports. This creates a
`depends-on-service` graph edge. Routes may import domain services, but never domain
internals; platform files may not import domains or routes.

Import the facade, then call `orders.getOrder.invoke({ orderId: "order-1" })`
exactly as you would call the original function descriptor.

There is no service dependency container, lifecycle API, middleware, or scoped
`context.service`. Runtime resources remain explicit function dependencies, while
HTTP policy belongs to routes.

An event-only domain and an integration domain may have no public functions.
`defineService({})` is therefore valid authoring syntax, but compilation rejects
a domain that owns no other graph-visible artifact. This keeps the runtime API
small without allowing empty placeholder domains into the application graph.
