`relkit.config.ts` is the root of one RELKIT application. The compiler evaluates it to connect the environment
contract, integration bindings, server policy, telemetry, Inspector, and optional deployment roles. Domain
handlers do not import this file.

## Read the generated configuration

<include cwd lang="ts" meta='title="templates/default/v1/api/relkit.config.ts"'>
  ../../templates/default/v1/api/relkit.config.ts
</include>

The API template starts local-only: one environment contract, bounded telemetry capture, an application
listener, and a separate Inspector listener. Cloud and deployment remain unselected unless the project was
created with those options.

Add an explicit application `id` before the application owns durable deployment state. Keep the same ID across
staging and production; stacks isolate environments. Changing a deployed application ID can make its resources
appear to have a new owner.

## Keep evaluation deterministic

Configuration describes topology. It must not open a database connection, call a remote API, start a server,
or create cloud resources during module import. Integration constructors describe bindings; runtimes activate
their clients only after the graph has passed validation.

Use each layer for one responsibility:

| Concern                                                          | Source of truth                                            |
| ---------------------------------------------------------------- | ---------------------------------------------------------- |
| Stable identity, ports, limits, telemetry, and binding selection | `relkit.config.ts`                                         |
| Runtime values and secrets                                       | The [environment contract](/docs/fundamentals/environment) |
| Business behavior                                                | [Functions](/docs/fundamentals/functions)                  |
| Public domain boundary                                           | [Services](/docs/service/define)                           |
| Adapter and infrastructure selection                             | [Integrations](/docs/integrations)                         |

## Verify a topology change

<Steps>
  <Step>
    ### Change one setting

    Edit `server.maxBodyBytes`, a provider profile, or another configuration value. Keep credentials out of
    literals and pass named secret bindings to integrations.

  </Step>
  <Step>
    ### Validate without starting the app

    ```sh title="Terminal — relkit-orders"
    bun run check
    bun run relkit graph print
    ```

    Expect one application graph with the configured bindings and no external provisioning.

  </Step>
  <Step>
    ### Restart listener changes

    Development can activate descriptor changes without dropping the last valid generation. Port and listener
    changes may require stopping and restarting `bun run dev`.

  </Step>
</Steps>

If a release check rejects a `docker(adapter)` binding, add a connected or supported infrastructure source.
Docker recipes are local development services and never become deployment resources.
