`relkit.config.ts` is the root of one RELKIT application. It connects authored descriptors to environment
contracts, provider profiles, server policy, telemetry, the inspector, and deployment. Business handlers do
not import this file; the compiler and runtime load it as the application boundary.

## Read the generated configuration

<include cwd lang="ts" meta='title="templates/default/v1/api/relkit.config.ts"'>
  ../../templates/default/v1/api/relkit.config.ts
</include>

The generated API template contains deliberately small defaults:

- `env` selects the only environment contract used by the application.
- Resource maps such as `events` name provider profiles that descriptors may request.
- `telemetry` controls capture policy, not arbitrary logging inside handlers.
- `server` and `inspector` own separate listeners and limits.
- `deployment` declares the intended target and adapter; it does not deploy during evaluation.

## Choose an application identity

An explicit application `id` is the stable identity used in graph and deployment state. Add one before the
application owns durable cloud resources or multiple stacks. Changing it later can make deployment treat the
application as a different owner.

For a generated local exercise, an inferred identity is enough. For a real orders service, use a domain name
such as `orders-api`, not a developer name, branch name, or environment name. Environment isolation belongs
to deployment stacks, so staging and production can share the application identity without sharing state.

## Apply a configuration change

<Steps>
  <Step>
    ### Change one runtime limit

    Edit `relkit.config.ts` and set `server.maxBodyBytes` to the largest request the application should accept.
    This is the global ceiling; an upload route may set a lower route-specific ceiling.

  </Step>
  <Step>
    ### Validate without starting the server

    ```sh title="Terminal — relkit-orders"
    bun run check
    bun run relkit graph print
    ```

    Expect a successful check and one application node. Configuration is evaluated as data; opening a
    network connection, reading a database, or creating cloud resources during module import is a defect.

  </Step>
  <Step>
    ### Restart the affected runtime

    Development reloads descriptor changes, but listener settings such as ports may require a process restart.
    Stop `bun run dev`, start it again, and verify the configured endpoint.

  </Step>
</Steps>

## Configuration boundaries

Use source-controlled configuration for stable policy and topology. Use the environment contract for values
that vary by machine, stack, or secret store. Put domain behavior in functions. This separation keeps graph
generation deterministic and prevents credentials from entering generated artifacts.

<Callout type="warn" title="Configuration is evaluated during checks">
  Keep `relkit.config.ts` deterministic and side-effect free. Provider constructors describe
  bindings; actual clients are created only when the runtime activates the checked graph.
</Callout>

## Diagnose common mistakes

<Accordions>
  <Accordion title="A descriptor cannot find its provider profile">
    Confirm the resource map uses the plural configuration key, the descriptor's `profile` matches
    the map key, and `defaults` selects a profile when more than one binding exists.
  </Accordion>
  <Accordion title="A secret appears in generated output">
    Replace the literal with an `env.secret()` declaration and pass that reference into the adapter.
    Rotate the exposed value before continuing.
  </Accordion>
  <Accordion title="Local configuration fails a production build">
    Read the production diagnostic. Process-local queues, caches, rate limits, or unprotected
    internal endpoints may be acceptable in development but invalid across replicas and restarts.
  </Accordion>
</Accordions>
