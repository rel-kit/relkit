title: Declared errors
description: Give expected failures stable data, HTTP behavior, and retry guidance without exposing internal defects.
---

A declared error is an expected domain outcome a caller can handle, such as a missing order or rejected state
transition. An unexpected exception is a defect: RELKIT records it internally and returns a safe boundary failure
instead of exposing a stack or provider detail.

## Define a stable failure

The `id` is the durable contract used by graphs, clients, traces, and matching. `data` limits the details callers
may receive. `http.status` contributes a typed HTTP response, while `retry` tells durable delivery whether another
attempt could help.

Register the descriptor in a function's `errors` list and throw the constructed declared value. Do not convert
every caught exception into a declared error; callers should depend only on failures the domain promises.

Expect HTTP `404` with the stable error code and validated data. Tests should assert those fields and the status,
not a complete internal message or stack trace.

## Treat retry as bounded guidance

- `"never"` means the same operation should not be retried automatically.
- `"later"` allows a durable transport to use its normal backoff.
- `{ kind: "later", afterMs }` supplies a minimum delay; the integration may wait longer.

HTTP and direct invocation do not automatically retry. Jobs and event delivery apply their own bounded policies,
so a retryable error never means an unbounded loop. See [Job retries](/docs/jobs/retries) and
[Event delivery](/docs/events/consume) for transport behavior.
