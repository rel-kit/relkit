title: Provider bindings
description: Connect logical resources to local, external, or managed infrastructure and understand ownership before deployment.

Descriptors declare logical dependencies such as a bucket, cache, job queue, event bus, model, or telemetry
sink. Provider bindings decide which implementation satisfies those dependencies in an environment. Keeping
that choice in configuration lets functions remain unchanged between local tests, an external service, and
managed cloud infrastructure.

The map key is a profile name. A descriptor may request that profile explicitly; `defaults` resolves omitted
profiles when more than one is configured. Adapter options reference the environment contract so credentials
and endpoints never become literal graph data.

## Choose ownership deliberately

<Tabs items={["Local", "External", "Managed"]}>
  <Tab value="Local">
    Use deterministic local providers for development and tests. Their state is normally process- or
    directory-scoped and must not be mistaken for production durability.
  </Tab>
  <Tab value="External">
    Use `external(adapter)` when another team, account, or system already owns the remote resource.
    RELKIT configures the runtime client but does not create or destroy that infrastructure.
  </Tab>
  <Tab value="Managed">
    Use `managed(adapter)` when the RELKIT deployment stack should provision the resource and
    permissions. Preview replacement and cost before apply; destroy may remove the managed resource
    and its data.
  </Tab>
</Tabs>

## Bind a new resource

<Steps>
  <Step>
    ### Define the logical descriptor

    Start with the bucket, cache, job, event, or model guide. Give durable resources stable IDs and select a
    profile only when the default should not apply.

  </Step>
  <Step>
    ### Declare environment inputs

    Add endpoint, region, resource name, and secret credentials to `src/env.ts`. Prefer role-based credentials
    supplied by the deployment platform when the adapter supports them.

  </Step>
  <Step>
    ### Add the profile

    Add the adapter under the matching plural map in `relkit.config.ts`, then wrap it in `external()` or
    `managed()`. If you introduce a second profile, update `defaults` or each descriptor intentionally.

  </Step>
  <Step>
    ### Verify without provisioning

    ```sh title="Terminal — relkit-orders"
    bun run check
    bun run relkit graph print
    bun run relkit deploy preview --stack development
    ```

    `check` validates references and capability compatibility. Preview is read-only for infrastructure and
    shows whether a managed binding would create, update, replace, or delete resources. Do not apply merely to
    test syntax.

  </Step>
</Steps>

## Operational questions to answer

Before choosing a provider, document durability, delivery guarantees, maximum object/message size,
retention, regional placement, expected concurrency, credentials, and ownership of deletion. Two adapters
implementing the same logical capability can have different operational ceilings.

<Callout type="warn" title="Managed means lifecycle ownership">
  A managed binding is not just a convenient client constructor. The deployment stack may create,
  replace, and destroy the backing resource. Use external ownership when data must outlive the
  stack.
</Callout>
