Declare an error when callers need to handle an expected failure, such as an order that does not exist. An unexpected exception is a defect: RelKit records it internally and returns a safe boundary failure
instead of exposing a stack or provider detail.

## Scaffold a typed error

From the application root, with an existing `orders` service:

```sh
bun run relkit add error receipt-rejected --service orders
```

Creates `src/services/orders/errors/receipt-rejected.error.ts` with `{ message: string }` data and
`retry: "never"`. It stays internal. Add it to the relevant function's `errors` list yourself;
a service bundle containing an error wires it to the bundle's example function automatically.

For every scaffolding flag, see the [error command reference](/docs/api/cli#relkit-add-error-name).

Every declared error needs an `id`. It becomes the public `code` in API responses, and graphs, clients and
traces use it to match the failure, so keep it stable when the file moves. `data` limits the details callers
may receive. `http.status` contributes a typed HTTP response, while `retry` tells durable delivery whether another
attempt could help.

Register the descriptor in a function's `errors` list and return the constructed error from the handler, as the
lookup example below does. Do not convert every caught exception into a declared error; callers should depend
only on failures the domain promises.

A function may declare an error its handler never raises. To catch stale declarations, turn on the
`unusedErrors` check in `relkit.config.ts`, and `relkit check` warns about each one:

```ts title="relkit.config.ts"
import { defineApp, defineEnv } from "@relkit/app/config";

export default defineApp({ env: defineEnv({}), check: { unusedErrors: true } });
```

The check only looks inside the handler, so an error raised from a helper function the handler calls is reported
as unused.

Expect HTTP `404` with the stable error code and validated data. Tests should assert those fields and the status,
not a complete internal message or stack trace.

## Treat retry as bounded guidance

- `"never"` means the same operation should not be retried automatically.
- `"later"` allows a durable transport to use its normal backoff.
- `{ kind: "later", afterMs }` supplies a minimum delay; the integration may wait longer.

HTTP and direct invocation do not automatically retry. Jobs and event delivery apply their own bounded policies,
so a retryable error never means an unbounded loop. See [task retries](/docs/modules/jobs/retries-and-idempotency) and
[Event delivery](/docs/modules/events/consume) for transport behavior.
