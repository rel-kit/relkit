RELKIT is a convention-first framework for TypeScript backend applications. You describe functions,
HTTP routes, asynchronous work, resources, and AI boundaries in ordinary source files. RELKIT compiles
those descriptors into one deterministic application graph and uses that graph everywhere.

<Callout title="Who these guides are for">
  You only need basic TypeScript. The guides explain RELKIT, Bun commands, HTTP behavior, provider
  configuration, testing, and deployment concepts when they first appear.
</Callout>

## Why RELKIT exists

Backend projects often describe the same operation several times: once in a handler, again in a router,
again in validation, again in OpenAPI, and again in deployment configuration. Those copies drift.
RELKIT makes the validated function the reusable unit and derives the surrounding transport and
operational artifacts from it.

```text title="The RELKIT application model"
TypeScript descriptors
        ↓
checked application graph
        ↓
development · tests · HTTP · jobs · events · OpenAPI · clients · inspector · deployment
```

The graph is not a second application that you maintain. It is generated output. You edit TypeScript
source, run `relkit check`, and let every consumer use the same checked result.

## The recommended sequence

<Steps>
  <Step>
    ### Create and run an application

    Follow [Start](/docs/start/create-an-app) through your first route and local development loop. This
    path requires no cloud credentials and does not create paid resources.

  </Step>
  <Step>
    ### Learn the reusable model

    Read [Service](/docs/service) for domains and public boundaries, then choose the HTTP, Events, Jobs,
    Database, Auth, Storage, Caching, or AI guide for the capability you need. Use
    [Application fundamentals](/docs/fundamentals/application) for configuration, schemas, errors, and context.

  </Step>
  <Step>
    ### Operate what you built

    Use the inspector, traces, deterministic tests, diagnostics, and deployment preview only after the
    application behavior is clear.

  </Step>
</Steps>

## Documentation and source of truth

Guide prose teaches when and why to use a feature. The [generated API reference](/docs/api/app) is the
source for exact signatures, while the [CLI reference](/docs/operations/cli-reference) is generated from
the same help model as `relkit --help`. Complete examples are included from tested template and commerce
source files so the documentation cannot silently preserve an old copy.

The canonical cross-feature application is
[`examples/commerce`](https://github.com/rel-kit/relkit/tree/main/examples/commerce). To report a problem,
open an issue in the [`rel-kit/relkit` repository](https://github.com/rel-kit/relkit/issues) with the
command, diagnostic code, and a minimal reproduction.
