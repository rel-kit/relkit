Mount a raw route when an integration already provides a native `Request`-to-`Response` handler. Use a [function-backed route](/docs/modules/http/define) for ordinary domain
operations that need RelKit input validation, declared errors, and generated contracts.

<Callout type="tip" title="Create the route from the terminal" icon="terminal">
  Use [`relkit add route --mode route`](/docs/modules/http/define#scaffold-a-route) to create a raw
  `GET` handler, then replace its placeholder with your integration. For Better Auth, use [`relkit
  add auth`](/docs/modules/auth/better-auth#scaffold-the-auth-baseline), which creates the
  specialized service and its `ALL` mount together.
</Callout>

## Mount an HTTP integration

A raw route uses `defineRoute({ handler: ... })` with a named method export. The handler accepts a
native `Request` and returns a `Response`, synchronously or asynchronously:

This route reads the native body itself and returns `202` with the started run. Do not combine `handler`
and `target`, or pass a raw handler to `defineServiceRoutes`. `ALL` is reserved for mounting Better Auth
yourself. Route file naming and collision checks still apply.

## Understand the boundary

| Behavior                                              | Function-backed route                              | Raw route                               |
| ----------------------------------------------------- | -------------------------------------------------- | --------------------------------------- |
| Entry point                                           | Public service function                            | Native HTTP handler                     |
| Input parsing and validation                          | Inferred or explicit mapping, then function schema | Owned by the adapter                    |
| Response construction                                 | Function output and declared response contract     | Adapter returns the complete `Response` |
| Function invocation context and declared dependencies | Available inside the target                        | No automatic function invocation        |
| Route `rateLimit`, `request`, and `responses` options | Supported                                          | Not part of the raw-handler API         |
| OpenAPI and generated-client operation                | Generated                                          | Excluded                                |

Framework request setup and matching HTTP middleware still surround raw routes. Do not assume this
makes arbitrary adapter body reads bounded or validates their payloads: configure the adapter's own
limits, signature checks, session security, and error handling. Use middleware or an upstream gateway
for transport policy that the raw-route API does not provide.

## Mount Better Auth yourself

RelKit mounts a Better Auth service at its `basePath`, so most applications have no auth route. To mount
it yourself, pass `mount: false` to `defineBetterAuthService` and export `ALL = defineRoute({ handler:
auth.handler })` from an optional catch-all route. The adapter owns those endpoints, which never require
a session; set `auth: "required"` on each function route that needs a signed-in caller. See
[Better Auth service](/docs/modules/auth/better-auth) for a complete setup and
[Protect routes](/docs/modules/auth/protect-routes) for requiring sessions and authorization boundaries.

## Verify the adapter separately

From the application root, run `bun run check`. Then test the adapter's paths, an unsupported method,
and its failure cases.
Assert the adapter's actual statuses, headers, and cookies; there is no generated route contract
to supply those assertions. Use the [testing guide](/docs/modules/operations/testing) for the application harness.
