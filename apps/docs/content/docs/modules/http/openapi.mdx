Generate an OpenAPI document from your application's checked routes, schemas, and declared responses. Paths, methods, request locations,
schemas, statuses, declared errors, rate limits, and operation IDs therefore come from authored descriptors
rather than a separate annotation file.

The document describes the HTTP routes, which are also what the generated client calls.
[Raw handlers](/docs/modules/http/raw-handlers) use a generic response contract because their adapters own the response.

## Generate the document

### Refresh checked artifacts

```sh title="Terminal — relkit-orders"
bun run check
```

Inspect `.relkit/generated/openapi.json` when no server is running. The file is generated; fix route or
schema source when it is wrong. It describes your application's routes only.

### Inspect the runtime document

```sh title="Terminal — relkit-orders"
curl http://localhost:3000/_relkit/v1/openapi.json
```

With your existing app's [Echo endpoint](/docs/modules/http/define#expose-one-public-function) running, confirm
`openapi` is `3.1.0` and find `POST /echo`. Use the configured backend port if it differs.
The commerce example uses `4000` and also includes `/orders/{orderId}`.

The served document is larger than the generated file. It adds the operations of a mounted
[Better Auth service](/docs/modules/auth/better-auth), such as `POST /api/auth/sign-in/email`, under
the Authentication tag. Do not compare the two expecting the same paths: the generated file has
only your routes. `HEAD`
and `OPTIONS` operations are in neither; see
[what the framework sends by itself](/docs/modules/http/responses#see-what-the-framework-sends-by-itself).

### Open the interactive reference

JSON OpenAPI needs no documentation UI package. To select Scalar, install its optional peer from
your application root, then set `server.apiDocs.ui` to `"scalar"` in your existing `relkit.config.ts`:

<include>/_snippets/generated/installations/scalar.mdx</include>

Restart the application after changing the selection. Startup validates the selected peer and
initializes the renderer before publishing readiness.

```sh title="Terminal — relkit-orders"
open http://localhost:3000/_relkit/v1/api-reference
```

Scalar renders the same protected document. Select an operation and verify parameters, request body,
success response, declared errors, and validation response.

Error responses use the `application/problem+json` media type. Each declared error gets its own
problem schema, with its `code` and `type` fixed to the error's ID and `data` set to the error's data
schema. The validation and rate-limit problems have schemas too. See
[Read an error response](/docs/modules/http/responses#read-an-error-response).

## What the contract lists

Each operation lists the Problem Details responses the server can send for it, in addition to the
responses its route declares:

| Status | Declared when                                                                |
| ------ | ---------------------------------------------------------------------------- |
| `401`  | The route has `auth: "required"`, or the function has an access rule         |
| `403`  | The function has an access rule                                              |
| `413`  | The request mapping reads a body                                             |
| `422`  | The operation reads path, query, header or body input                        |
| `429`  | The route has a rate limit, with the `RateLimit-*` and `Retry-After` headers |
| `500`  | Always, for a function-backed route                                          |

The error bodies refer to one `Problem` schema in `components.schemas`; the validation, oversize and
rate-limit bodies narrow it with `allOf`. A response that the route declares itself replaces the
generated one for that status. A status the server cannot send for an operation is not listed: a
`GET` without input has no `422` and no `413`. Raw handlers keep a single `default` response. The
document leaves out answers that depend on deployment, such as `403` from the transport policy and
`502`; see the table of [framework answers](/docs/modules/http/responses#see-what-the-framework-sends-by-itself).

## Operation identity and compatibility

OpenAPI's operation ID and the generated client's procedure key use the checked route ID. Changing a
path or method changes the inferred ID unless it is pinned explicitly. Moving a private function
without changing its route does not rename the endpoint. Compare generated contracts in review and
treat removed paths, newly required inputs, and narrowed outputs as compatibility decisions.

## Protect production documentation

<Callout type="warning" title="Production documentation is opt-in">
  Enable `server.apiDocs.enabledInProduction` only with internal-endpoint authorization. Scalar
  embeds the protected OpenAPI document; protect the raw JSON endpoint as well as the UI. Enabling
  production docs without the required authorization configuration causes a startup configuration
  error.
</Callout>

In development and test, JSON OpenAPI is available independently of the UI. Scalar is disabled by
default; `server.apiDocs.ui: false` leaves the JSON document available without loading Scalar.
`server.apiDocs.excludeDomains` filters the served document; it does not disable those domains'
routes, revoke access, or remove generated-client operations. Documentation visibility is not authorization.

Disabling the public reference does not remove the build-time `openapi.json` artifact. Release tooling can
publish it to a controlled developer portal without exposing introspection from every application instance.
