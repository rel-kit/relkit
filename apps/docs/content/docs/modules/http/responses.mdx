A function-backed route turns the function's validated result or declared error into an HTTP response. Start with inference;
override the transport only when the public HTTP contract needs it. Keep reusable errors in the
[domain's error declarations](/docs/learn/concepts/errors).

## Understand inferred responses

| Outcome                                       | Default response                         |
| --------------------------------------------- | ---------------------------------------- |
| Non-void function output                      | JSON `200`                               |
| `void` or `undefined` output                  | Empty `204`                              |
| Request mapping or input validation failure   | Validation problem `422`                 |
| Declared application error                    | Its `http.status`, or `500` when omitted |
| Route rate-limit rejection                    | Problem `429`                            |
| Invalid function output or an internal defect | Problem `500` without internal detail    |

Runtime failures can also produce responses such as provider failure `502` or timeout `504`.
The inferred OpenAPI list is not an exhaustive list of infrastructure or middleware failures.
Undeclared exceptions are not a way to create a public error contract.

## Read an error response

Every error response is [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) Problem Details with the
`application/problem+json` content type. A declared error looks like this:

```json
{
  "type": "/errors/orders.not-found",
  "title": "Not Found",
  "status": 404,
  "code": "orders.not-found",
  "detail": "Order order-1 was not found",
  "data": { "orderId": "order-1" },
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

- `code` is the declared error's ID, or one of RelKit's codes below. Branch on `code`, not on
  `detail`, which is text for people.
- `data` is the error's validated data. Only declared errors carry it, and rate limits.
- `issues` appears on validation problems, with one `code`, `message` and `path` per issue.
- `traceId` matches the request's trace, so you can find it in the Inspector and in your logs.
- A declared error that retries later, and a rate-limit rejection, also send `Retry-After` in seconds.

| Status | `code`                         | When                                                  |
| ------ | ------------------------------ | ----------------------------------------------------- |
| `401`  | `unauthenticated`              | The route requires a session and the request has none |
| `403`  | `origin-denied`, `csrf-denied` | The transport policy rejects a state-changing request |
| `404`  | `not-found`                    | No route matches the path                             |
| `405`  | `method-not-allowed`           | The path exists for other methods, listed in `Allow`  |
| `413`  | `payload-too-large`            | The body is larger than the server's limit            |
| `422`  | `validation`                   | Request mapping or input validation failed            |
| `429`  | `rate-limited`                 | The route's rate limit is exhausted                   |
| `499`  | `cancelled`                    | The client went away before the response              |
| `500`  | `internal-error`               | An unexpected defect or invalid output                |
| `502`  | `provider-failure`             | A dependency of the request failed                    |
| `504`  | `timeout`                      | The request ran past its deadline                     |

In production, `500` and `502` problems never contain internal detail. In development and test, their
`detail` names the redacted cause.

The Orders `POST` returns JSON `201`; its output schema and declared errors still come from
`createOrder`. The route above does not use an explicit `responses` array.
Use `successStatus` for this case instead of copying all inferred response declarations.

`HEAD` invokes the target but removes the response body. `204` responses are empty as well;
do not choose `204` when callers need the returned JSON.

## Set headers and cookies from the output

A route's `response` option computes the status, headers and cookies from the function's validated
output. The Orders `POST` above uses it to send `Location: /orders/<orderId>`. The function itself
does not change, so a job or tool that calls `createOrder` still gets only its output.

```ts
response: (order) => ({
  status: 201,
  headers: { location: `/orders/${order.orderId}` },
  cookies: [{ name: "last-order", value: order.orderId, httpOnly: true, sameSite: "Lax" }],
}),
```

`status` must be a `2xx` other than `205`, and it replaces `successStatus` for that response; OpenAPI
still documents `successStatus`. The option runs only for successful responses. If it throws or
returns an invalid status, the request fails with a `500` problem.

## Replace the complete response contract only when needed

An explicit `responses` array replaces inference. The [Routes API](/docs/api/routes) provides:

| Helper                                 | Declaration                                                 |
| -------------------------------------- | ----------------------------------------------------------- |
| `http.success(status, schema)`         | Successful output and status                                |
| `http.error(errorId, status, schema)`  | Status for a declared application error and its data schema |
| `http.validationError(status, schema)` | Validation response; status defaults to `422`               |
| `http.response(id, status, schema)`    | A named generic response declaration                        |

Include success, validation, declared application errors, and any other outcomes the endpoint
promises. Omission does not prevent a runtime failure; it can leave the generated contract incomplete.
An omitted application-error mapping falls back to an internal error rather than a declared status.

Declarations are not branch handlers. Ordinary successful invocation uses the first success
declaration (or the first generic response when there is no success declaration). Listing several
success statuses does not select one based on returned data. These helpers do not define response
headers or content negotiation, and adding a `3xx` declaration does not implement a redirect.

Use [middleware](/docs/modules/http/middleware) for response headers and transport short-circuits. For an
adapter that owns redirects, binary bodies, or another HTTP protocol, consider a
[raw handler](/docs/modules/http/raw-handlers) and document its separate contract.

## Distinguish request failures from server failures

Input schema and mapping failures return `422` by default. That includes malformed JSON and
unsupported body content types in the request mapper. The framework's global Content-Length
check can reject an oversized request with `413`; a byte-limit failure encountered later while
mapping the body is a validation response. Test the layer your client actually reaches.

Function output is validated by the invocation engine. Invalid output is a server defect, not
a caller's `422`. Additional explicit response-schema checks run in development and test mode;
do not use a response-only schema as the sole production validation boundary.

## Verify status, headers, and body together

With the [Echo endpoint](/docs/modules/http/first-route) running on port `3000`:

```sh
curl -i -X POST http://localhost:3000/echo \
  -H 'content-type: application/json' \
  -d '{"message":"hello"}'
curl -i -X POST http://localhost:3000/echo \
  -H 'content-type: application/json' \
  -d '{"message":""}'
```

Expect JSON `200` for the first request and validation `422` for the second. Add tests for every
declared application error and middleware rejection in your own endpoint. A correct body with the
wrong status is still a broken HTTP contract.

Middleware-only responses are not automatically added to OpenAPI or the generated client's error
types. Describe them explicitly, and test the [RPC client](/docs/modules/http/generated-clients) separately:
it does not consume the REST response envelope.
