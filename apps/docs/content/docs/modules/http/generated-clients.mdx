Generate a typed client so callers can use your routes without maintaining their own request and response types. Each route
appears on the `api` object under its target function's ID, in camelCase: `orders.create-order`
becomes `api.orders.createOrder`. Input, output, and declared application errors come from the
target functions.
Raw handlers do not become generated-client operations.

The client calls **the REST routes themselves**: `api.orders.createOrder(input)` sends the same
request the [OpenAPI document](/docs/modules/http/openapi) describes, so curl can reproduce any call.
It reads each route's request mapping from the backend (`/_relkit/v1/client/routes`) and places every
input field in the path, query, headers or body the route reads it from. A route is also reachable by
its stable route ID and its `METHOD /path` name on the raw client. Channels, agents and jobs, which
have no REST route, use RelKit's own endpoint at `/_relkit/v1/rpc`.

## Generate the contract

From your application's root:

```sh
bun run check
```

This writes `.relkit/generated/contract.ts` and `.relkit/generated/client.ts`, alongside graph,
OpenAPI, and JSON client-contract artifacts. Never hand-edit them.

Make the generated contract part of the caller's TypeScript program: import the generated client
entry point, or explicitly include the generated contract when using `@relkit/client` directly.
The contract augments the default client registry so the `api` tree and its inputs are typed. Merely
installing `@relkit/client` in another app does not teach it your server's operations.

Package or share the generated client and contract together with the dependencies they import.
Regenerate and review them when route identities, input, output, or errors change.

The same generated contract includes public task-first jobs under `jobs.<name>`. A job trigger returns an
accepted `runId`; inspect, watch, and control it through the generated `runs` procedures rather than treating
the trigger response as the task output. Keep the original operation ID and request when an acceptance response
is unknown.

</Step>

The snippet uses port `3000`, the generated-app default. Change it to `4000` when calling the commerce

`headers` accepts a header collection or a provider, including an asynchronous provider.
Use request-scoped headers or a provider for credentials; do not mutate one shared instance with
different users' credentials in a server process. The example's mutable `liveHeaders` is not a
multi-user session store. Browser credentials default to `include`; cross-origin cookies still
require appropriate browser, cookie, and server CORS configuration. A custom `fetch` is supported.

route targets the function `echo.echo`, so you call `backend.echo.echo({ message: "hello" })` on the
tree that `createApi` returns. It resolves to the function's validated output, not a native
`Response`.

`createApi` does not load identity automatically. This browser example performs the identity
handshake first and includes its scope and session epoch on the mutation, as the React provider does.

See [the route declaration and React button](/docs/modules/http/define#use-from-the-frontend)
side by side, or follow [Call your API from React](/guides/frontend/connect-react) to connect
a separate frontend. [Client transports](/docs/modules/client/transports) covers HTTP,
WebSocket, and automatic transport selection.

| Original REST route                                     | Generated RPC call                                        |
| ------------------------------------------------------- | --------------------------------------------------------- |
| Maps path, query, headers, cookies, and body into input | Accepts the target function's input directly              |
| Uses the route's `request` mappings and transforms      | Does not replay those mappings or transforms              |
| Returns the selected HTTP success status and body       | Resolves to typed function output                         |
| Returns an HTTP error envelope                          | Rejects with an error keyed by `code`                     |
| Handles multipart according to the route                | Does not automatically reconstruct that multipart request |

For example, the Orders REST route obtains `orderId` from `idempotency-key`; an RPC caller supplies
the function's `orderId` input property. Sending that header alone does not fill the RPC input.
Likewise, catch-all input is an array supplied to the function, not a REST path the client constructs.

## Handle failures by contract

A rejected call carries a `code`, `status`, and `data`. Declared application errors keep their
stable error ID as `code`, such as `orders.not-found`, with their validated data. Other failures use a
fixed list of codes, such as `UNAUTHORIZED` or `INTERNAL_SERVER_ERROR`, and `NETWORK_ERROR` when no
response arrived. Checking `code` narrows `status` and `data`, so branch on it rather than on
`instanceof ORPCError` or a formatted message. Do not expect a REST validation `422` body to be the RPC error shape.

A response returned by HTTP middleware is not automatically a declared function error. The RPC
middleware bridge maps a returned `401` to `UNAUTHORIZED`, a `429` to `TOO_MANY_REQUESTS`, and other
returned responses to `INTERNAL_SERVER_ERROR`. Test these cases if middleware protects the operation.

## Test security at both entry points

Registered Better Auth protection and route policy run with the operation's canonical method/path.
A route marked `client: false` stays out of the generated client and its routes document.

Point the client at a running local test server. The current `createTestApplication` HTTP helper does
not serve the client routes document, so connecting it through a custom `fetch` is not a client
integration test.
Cover success, invalid input, a declared error, missing credentials, and any quota policy.
Client tests exercise the same request mapping as REST tests. See [Testing](/docs/modules/operations/testing)
for the other available test layers.

## Review compatibility changes

Changing an inferred route ID renames the client operation. A required input field, a removed error
code, or a narrowed output can break consumers even if the server compiles. Compare generated
artifacts in review and version shared contracts with their callers.
