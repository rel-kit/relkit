An integration connects a RELKIT capability to a provider, such as S3 for files or Redis for cached values. Services, functions, routes, and events
depend on checked capability contracts; integrations connect those contracts to Redis, S3,
telemetry exporters, local Docker services, and deployment platforms.

<Callout type="tip" title="Start here" icon="route">
For your first local integration, follow [Cache product prices](/guides/caching/cache-product-prices) for Redis or [Upload product images](/guides/storage/upload-product-images) for MinIO. Both include installation, configuration, and verification. The [integration references](/docs/api#integrations) list each package's exact APIs.
</Callout>

## Pre-setup

Start with a working minimal app and Docker. Install the owner of each selected adapter,
then bind it in `relkit.config.ts` through `defineApp`. Use `docker(adapter())` when it has
a local recipe; the wrapper supplies development connection values. Follow the module's
setup before adding its first resource:

Named connection bindings such as `binding.secret(...)` select provider values; `defineEnv`
declares application values available to functions. Keep the distinction when configuring
[environment contracts](/docs/learn/concepts/environment). Run `bun run check` before
`bun run dev`; a package installation alone creates no profile or running resource.
The [Docker coverage table](/docs/modules/integrations/local-docker#supported-local-services)
identifies providers without a recipe.

## Understand ownership

Connected adapters wire a resource that already exists. `docker(adapter)` selects the adapter's local recipe
for development only. Infrastructure wrappers such as `aws(adapter)` let the deployment stack own a resource.
The deployment engine and host are separate roles, so selecting AWS hosting does not claim every connected
Redis, S3-compatible, Cloudflare, or model resource.

Run `bun run check` to validate package registration, source wrappers, profile selection, and deployment-role
compatibility before starting a runtime or previewing infrastructure.

## Declare authoring entrypoints

If you are implementing an adapter, begin with [Provider authoring](/docs/modules/integrations/provider-authoring) for a maintained example and validation steps. Use [Local providers](/docs/modules/integrations/local-providers) when explicitly owning local runtime state.

Integration package authors list their application authoring entrypoints in
`package.json` under `relkit.integration.exports.authoring`. Use a string for one exact export,
such as `"."`, or an explicit list when multiple authoring leaves are public:

```json
{ "authoring": [".", "./sqlite", "./pg", "./mysql"] }
```

Every listed leaf must also exist in the package's `exports` map. The compiler accepts only those
exact imports; listing a parent does not permit its children. Wildcards and path traversal are
rejected. Drizzle declares its three dialect model entrypoints, and Better Auth declares its root
and `./drizzle` bridge. Runtime internals, React adapters, and testing helpers do not become
application authoring entrypoints through this declaration.
