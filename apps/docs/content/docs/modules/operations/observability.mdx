## Understand capture order

```text title="Telemetry flow"
runtime event
→ canonical record
→ capture policy
→ redaction
→ bounded retention and live Inspector stream
→ root trace-consistent sampling
→ independent exporters
```

Local capture is independent of external sampling. With `traceRate: 0.25`, the bounded Inspector store can keep
a complete redacted local trace even when that trace is not selected for remote export. Spans, logs, and errors
with the same trace use the same deterministic trace decision. Log export also follows `minimumLogLevel`.
Configure `traceRate: 1` when a Collector performs tail sampling and needs complete failed traces; RELKIT does
not keep a second in-process tail-sampling buffer.

`localRetention` bounds record count, age, and bytes. It is diagnostic evidence, not durable business storage.

Application logging and production telemetry use bounded memory unless a storage capability is explicitly
supplied. They do not install or open DuckDB. Normal console output and external exporters remain usable
without development history. The default memory store keeps at most 1,024 records and 4 MiB of encoded
record payloads; explicit retention settings can lower or change those bounds.

## Read development logs

`bun run dev` prints startup URLs, compilation and reload outcomes, HTTP completions, and application output.
The default terminal level is INFO. Use `bun run dev -- --verbose` for DEBUG events and retained error details,
`--log-level warn` to select an explicit threshold, `--no-color` for plain text, or `--json` for newline-delimited
records on stderr. An explicit level overrides verbose's DEBUG selection. `NO_COLOR` and redirected output also
disable color. Terminal filtering does not reduce captured history.

Persistent development history belongs to the separately installed and launched
[@relkit/inspector tool](/docs/modules/operations/inspector). Complete its install → bridge enablement → tool
startup procedure before using these views. It owns `@relkit/observability-local`, DuckDB and the Node
worker; the backend-only workflow continues to require only Bun.

The tool defaults to `.relkit/observability/observability.duckdb` under its selected project root.
Use the tool's `--history-directory` option for an explicit persistent override. One Inspector writer
owns a history directory, which is bound to one project. Stopping/restarting the tool or reloading the
backend preserves committed history; removing a package-runner cache does not remove project history.

Before collection, an enabled backend bridge holds only a bounded redacted buffer, initially 2,048
records/2 MiB. With no running tool there is no new persisted tool history. Overflow or failed delivery
is reported as incomplete capture; collector receipts acknowledge committed session/sequence records
and deduplicate replay. Backend capture limits and tool history retention are separate budgets.
Exporter delivery remains independent of collector acknowledgments.

The current store uses observability model v2. Moving store ownership preserves existing database schemas,
receipt identities, imported segment markers, and source history files. Incompatible development state is not
reset automatically: RELKIT reports `RELKIT_OBSERVABILITY_STATE_INCOMPATIBLE` and preserves the directory for
diagnosis. Diagnostic history does not own durable job, checkpoint, provider, or agent application state.

If storage fails, application requests continue. The Logs workspace reports degraded storage and failed or
dropped records. Restart the Inspector after fixing the cause; records that failed to commit are not saved.

## Redact before storage or export

`development-redacted` allows bounded invocation and operation input/output capture while replacing protected keys and known secret values.
`maxBytes` is required and prevents oversized content from being retained. Mode `off` omits protected payload
content entirely.

<Callout type="danger" title="UI masking is too late">
  Authorization and cookie headers, environment secrets, provider credentials, request bodies,
  prompts, and model results must be removed or redacted before persistence, streaming, or exporter
  queues.
</Callout>

Use synthetic secrets in tests and assert that they do not appear in records, diagnostics, generated artifacts,
or exporter payloads. Redaction is a safety boundary, not permission to log credentials.

## Diagnose exporter health

Exporter fan-out is isolated. A failed Sentry or OTLP exporter cannot block application work or the other
exporter. Failures increment health counters and create redacted local-only diagnostics that are not sent back
through the failed exporter.

Start the app and follow one identifiable request:

```sh title="Terminal — relkit-orders"
bun run dev
curl http://localhost:3000/hello\?name=Telemetry \
  -H "x-correlation-id: docs-telemetry"
```

After the separate [Inspector setup](/docs/modules/operations/inspector), open **Requests**, select `/hello`, and follow its trace, logs, graph hash, generation, and
activation fingerprint. The trace timeline numbers and connects spans and lifecycle events by their recorded
date/time, labels each operation type, and keeps overlapping duration bars visible for concurrent work. Select
a span to open the expanded sheet with separate input, output, outcome, and metadata sections alongside its
resource attributes, events, links, correlated logs,
and safe error details. Event and job continuations remain separate links because they can outlive the HTTP
response. If remote telemetry is silent, inspect exporter health, queue depth, failure count, and drop count
before assuming application capture failed.

## Add application trace detail

RELKIT already creates spans for routes, functions, declared client operations, jobs, events, tools, and agents.
Use `context.trace` only for application work that those boundaries do not describe:

| Operation                                    | What it records                                                      |
| -------------------------------------------- | -------------------------------------------------------------------- |
| `span(name, callback)`                       | An `internal` child span around the callback                         |
| `span(name, { attributes, kind }, callback)` | A child span with initial attributes and kind `internal` or `client` |
| `event(name, attributes?)`                   | A point-in-time event on the active span                             |
| `setAttributes({ key: value })`              | Additional attributes on the active span                             |

The callback passed to `span` runs with a child span as the active span. RELKIT ends it on success or failure and
returns or rethrows the callback result unchanged. The default kind is `internal`; use `client` only for a custom
outbound dependency RELKIT does not already instrument. Nested and parallel callbacks keep the correct parent.

`event` adds a point-in-time event to the active span. `setAttributes` adds facts to that same active span, so a
call directly in a handler annotates the handler's invocation span while a call inside `span` annotates the child.
There is no manual start or end API.

Attribute values are limited to strings, finite numbers, and booleans. Names beginning with `relkit.` and identity
keys such as `traceId`, `spanId`, and `requestId` are reserved for the runtime. Recording is bounded; Inspector
reports dropped or truncated data instead of implying that omitted telemetry was observed. Do not put secrets,
payloads, or high-cardinality values such as random IDs into attributes.
