A realtime channel sends live application updates to clients that are currently connected. An order-status change, a new announcement, or a dashboard invalidation are good channel events.

<Callout type="tip" title="Start here" icon="route">
Start with [provider setup](/docs/modules/realtime/providers), then follow the announcement example below and [connect a React subscriber](/docs/modules/realtime/react). The [Realtime reference](/docs/api/realtime) lists channel declarations and operations.
</Callout>

The channel is not your database. Load the current state from an ordinary route, then use channel events to update or invalidate that state. This distinction makes refresh and reconnect behavior predictable: the route restores the truth, while the channel keeps the page current.

## Realtime channels or application events?

RELKIT has two event-shaped features with different jobs:

| Use                                            | Choose                                       | Why                                                     |
| ---------------------------------------------- | -------------------------------------------- | ------------------------------------------------------- |
| Notify browsers that are viewing a resource    | Realtime channel                             | It supports scoped subscriptions, replay, and presence. |
| Run backend work after something happens       | [Application event](/docs/modules/events)    | It delivers work to server-side consumers.              |
| Return a sequence to the caller of one request | [Typed stream](/docs/modules/http/streaming) | Its lifetime belongs to that request.                   |

A function may publish both an application event and a channel update when both outcomes are needed. Neither mechanism replaces the other.

Use a [job watch](/docs/modules/jobs/clients) for one accepted durable run. Realtime channels remain application
notifications and do not become a substitute for task output, run status, or provider-backed recovery.

## The Realtime API

| API                     | What you use it for                                                                 |
| ----------------------- | ----------------------------------------------------------------------------------- |
| `defineChannel()`       | Declare partition parameters, event payloads, browser access, replay, and presence. |
| `channel.trigger()`     | Append one validated event from backend code.                                       |
| `channel.getPresence()` | Read declared presence without joining the channel or changing its leases.          |
| `useChannel()`          | Observe one typed channel partition from React.                                     |
| `useRealtime()`         | Manage subscriptions directly when a hook per channel is not convenient.            |

### Subscribe from the frontend

<include>/_frontend/channel.mdx</include>

The declaration controls both publication and generated client types:

| Option     | Meaning                                                                           |
| ---------- | --------------------------------------------------------------------------------- |
| `id`       | Stable channel name used by backend and generated clients.                        |
| `params`   | Schema that identifies a partition, such as one `orderId`.                        |
| `events`   | Map of event names to their payload schemas.                                      |
| `client`   | Omit for backend-only use, set `public: true`, or provide an authorization guard. |
| `replay`   | Optional retention window and maximum event count for reconnects.                 |
| `presence` | Optional connection count or protected member projection.                         |
| `profile`  | Provider profile; otherwise the application default is used.                      |

An empty `events` map is valid only for a presence-only channel. Event binding is never an access-control boundary; browser access always comes from `client`.

This declaration generates the browser selector `announcements.feed`. The
[frontend subscriber example](/docs/modules/realtime/react#subscribe-to-a-channel) shows its typed
`posted` callback, authoritative route query, and reconnect recovery.

RELKIT validates the partition parameters and payload before appending the event. The returned receipt contains the event ID, checkpoint, provider profile and epoch, and whether an idempotent request was a duplicate.

`accepted: true` means the provider stored the append and its receipt atomically. It does not mean every subscriber received the event. A subscriber can disconnect immediately after the append and recover according to the channel's replay policy.

For a retryable publish, pass an `idempotencyKey` created by RELKIT. Reusing the same UUIDv7 key with the same channel, partition, event, and payload during the 24-hour receipt window returns the original receipt. Reusing it for different content fails. Without a key, retrying after a lost response may append the event twice; RELKIT never retries it automatically.

If a database update and publication must succeed together, write an outbox entry in the same database transaction and publish from the outbox. Calling `trigger()` after a database write does not make the two operations atomic.

## Run the backend example offline

The snippets above belong to the repository's `examples/commerce` app. From the repository
root, with dependencies installed, run its focused HTTP test:

```sh title="Terminal — RELKIT repository root"
bun test examples/commerce/tests/http.test.ts
```

The test creates an application with an isolated local realtime provider, posts announcements
through the public HTTP route, and reads them back. Expect two passing tests; no Docker or
frontend is needed for this check. A passing test proves the function can append its channel
event, but does not prove browser delivery or reconnect behavior. The
[React guide](/docs/modules/realtime/react) connects a browser after this backend path works, and
[Providers](/docs/modules/realtime/providers) explains the local Redis setup for a live server.
