## Classify the outcome

RELKIT has no implicit offline write queue. A known-offline write is `not-sent`; a lost response after
transmission is `unknown`. Agent runs, controls, and continuations use scoped operation IDs and durable
receipt lookup after refresh. Arbitrary mutations remain unknown unless the application supplies a
reconciliation endpoint. Do not resubmit an uncertain external effect automatically.

Job submissions additionally retain the original operation ID, idempotency key, request digest, and any
provider-certified recovery window. A recovered job must use the same request; a discarded `runId` is not a
safe recovery strategy.

## Choose recovery from the outcome

The public `isJobUnknownOutcome` guard tells you whether a caught value includes a job
recovery action. Show that action to the user or use it in an explicit reconciliation flow:

The client cannot infer whether a disconnected write reached your backend. For jobs, keep the
original operation ID and request digest and follow the provider-certified recovery action.
