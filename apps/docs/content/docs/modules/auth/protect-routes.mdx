Require a session on selected routes after mounting Better Auth. This HTTP access check answers
“is the caller signed in?” It does not answer “may this caller access this order?”

<Callout type="note" title="Before you begin" icon="clipboard-check">
  Before using this guide, complete [Better Auth installation and
  configuration](/docs/modules/auth/better-auth) and apply the database migrations. The minimal app
  does not include the optional auth SDK.
</Callout>

## Mount the API

RelKit mounts the Better Auth service's handler at `/api/auth`, owning that path and the auth endpoints
under it. They are Better Auth's native endpoints, not typed function routes, so they do not become
RelKit OpenAPI or client operations. Auth endpoints never require a session, so callers can always sign in.
See [Better Auth service](/docs/modules/auth/better-auth) to set it up.

Set `auth: "required"` on each function route that needs a signed-in caller:

RelKit checks the session before the route's middleware and its function run. Routes without the option
stay public. The middleware and the function then read the same session: RelKit looks it up once per
request. If the application mounts no Better Auth route, `relkit check` reports
[`RELKIT_ROUTE_AUTH_UNAVAILABLE`](/docs/errors/relkit-route-auth-unavailable), and such a route answers every
request with `401`.

The [MCP endpoint](/docs/modules/ai/mcp) is not a route. To limit it to signed-in callers, set
`server.mcp` in `relkit.config.ts`:

```ts title="relkit.config.ts"
import { defineApp, defineEnv } from "relkit/config";

export default defineApp({ env: defineEnv({}), server: { mcp: { auth: "required" } } });
```

## Handle an unauthenticated request

A request without a valid session receives a `401` [problem](/docs/modules/http/responses#read-an-error-response):

```json
{
  "type": "/errors/unauthenticated",
  "title": "Unauthorized",
  "status": 401,
  "code": "unauthenticated",
  "detail": "This route requires a signed-in session.",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

RelKit does not redirect the browser to a login page. Your frontend handles the response and offers a
sign-in flow. Preserve a safe, validated return destination if you redirect after authentication;
do not turn arbitrary input into an open redirect.

With the example running, verify the access check from another terminal:

```sh
curl -i http://127.0.0.1:3000/account/profile
curl -i http://127.0.0.1:3000/session
```

Expect `401` for the protected profile and `200` with `authenticated: false` for the public session
operation. Then follow [Your first auth flow](/guides/auth/email-password-sign-in) to repeat the protected request
with a valid cookie.

## Add an access rule to a function

Route protection applies to HTTP requests, not every direct invocation of its target. To decide who may
call a function from anywhere, give the function an `access` rule:

```ts title="src/services/orders/functions/refund-order.function.ts"
import { defineFunction } from "relkit/functions";
import { s } from "relkit/schema";

export const refundOrder = defineFunction({
  id: "orders.refund-order",
  input: s.object({ orderId: s.string() }),
  output: s.object({ refunded: s.boolean() }),
  access: {
    roles: ["admin", "support"],
    permissions: ["orders:refund"],
    allow: ({ session, input }) => session !== null && input.orderId !== "locked",
  },
  handler: async () => ({ refunded: true }),
});
```

Every part you set must pass: the caller needs at least one of `roles`, every `resource:action` entry in
`permissions`, and `allow` must return `true`. `allow` receives the session (or `null`), the validated input
and the caller. RelKit checks the rule before the function's handler for every caller: HTTP routes, jobs,
tasks, event consumers, tools, agent tool calls, MCP and the runtime handle. A call from inside another
function, such as `ctx.functions.refundOrder(...)`, is checked as the caller of the outer function.

| Caller                            | Outcome when the rule fails                                    |
| --------------------------------- | -------------------------------------------------------------- |
| Signed-in user without the rule   | `access-denied`: HTTP `403`, the coded error for other callers |
| No session                        | `unauthenticated`: HTTP `401`, the coded error otherwise       |
| `getRelkit()` or `createRelkit()` | Runs as `system`, which passes every rule                      |
| `relkit.as(session).functions...` | Decided by that session's roles and permissions                |

Roles and permissions come from Better Auth. With the
[organization plugin](https://www.better-auth.com/docs/plugins/organization), the roles are the user's member
role in the session's active organization, and permissions are checked against the plugin's access control.
Without it, roles come from the admin plugin's `user.role`, and no permission is granted.

Jobs, tasks and event deliveries run without a session, so a function with an access rule fails with
`unauthenticated` when they call it. Call it through `getRelkit()` to act as the application, or through
`relkit.as(session)` to act as a user:

```ts
import { getRelkit } from "relkit/functions";

await getRelkit().as(session).functions.orders.refundOrder({ orderId });
```

## Check ownership in the function

An access rule decides who may call the function. A request for another user's order still needs an
ownership or membership check: read the verified identity with [session lookup](/docs/modules/auth/sessions),
or use `allow`, and constrain the query to rows the caller owns. Derive the caller's identity from the
session, not from an input such as `userId`, `organizationId`, or `role`. Keep privileged role assignment
server-owned. A generated database client is not row-level authorization, and a service export is not an
access-control rule.

## See protection in OpenAPI and the Inspector

A route with `auth: "required"`, or one whose function has an access rule, declares the `session` cookie
security requirement and `401` and `403` problem responses in OpenAPI, with the rule under `x-relkit.access`.
The graph records the rule on the function node, and the Inspector shows it next to the route's auth
requirement in its graph and route views.
