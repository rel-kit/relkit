Use `defineBetterAuthService` to add Better Auth credentials, accounts, and sessions to your application. RelKit discovers it, activates
the application's Drizzle connection first, and passes that native client to Better Auth's Drizzle
adapter. Better Auth handles credentials, accounts, sessions, and its HTTP protocol.

The current integration requires exactly one Drizzle service, one Better Auth service, and one
filesystem `ALL` catch-all mount for that auth handler. Do not construct a second connection for auth
or register the descriptor as a member of an ordinary `defineService`.

## Pre-setup

Use [authentication setup](/docs/modules/auth#pre-setup) to start local Docker PostgreSQL,
declare the database/auth fields with `defineEnv`, and supply a stable secret before startup.
If you completed that scaffold, skip installation below and customize the existing files.
Existing SQLite/MySQL applications keep their dialect and applied migration history.

## Install compatible packages

Authentication is optional in a minimal app. Choose one setup path from the backend root.
Keep existing database tables, patches and overrides when merging these fields.

### Scaffold the auth baseline

```sh title="Terminal — application root"
bun run relkit add auth --adapter better-auth --database-dialect postgresql
```

This creates the Better Auth file `src/services/auth/better-auth.ts` and its service
`src/services/auth/service.ts`, merges auth environment declarations, and installs the selected adapter, native SDKs,
declaration peers and repairs. It reuses the existing Drizzle service or creates one when absent.
`--database-dialect` must match an existing database; when none exists, it chooses the new dialect.

For an existing database, the scaffold adds `schema/auth.ts` and exports its tables from the
schema index. Review those additions, preserving business tables and applied migrations.
Existing auth table names cause a collision instead of being overwritten. The scaffold does not run migrations,
generate a secret, or protect business routes. Configure those before accepting sign-ins.

Run this once when the app has no auth service. If it already exists, edit its Better Auth file.
With `--no-install`, run `bun install` and `bun run check` before continuing. See the
[auth command reference](/docs/api/cli#relkit-add-auth) and
[complete sign-in guide](/guides/auth/email-password-sign-in).

The backend requires no React package. `@relkit/better-auth` contains lazy declarations and session
types; generated servers select `@relkit/better-auth/drizzle` for native activation. Applications
using the native Effect layers or `activateBetterAuthService` directly import them from that same
`/drizzle` entrypoint. React belongs to `@relkit/better-auth/react` and is installed only for a
selected React client. Better Auth and Drizzle remain application-owned SDK dependencies; their
actual upstream dependencies are retained.

The generated setup includes the Better Fetch declaration override and application-owned Drizzle
patch. `relkit add auth` plans those selected fields automatically; manual consumers must merge them
and reinstall. The Cloudflare package above supplies the
real `D1Database` type imported by this SDK's declarations; it is a development requirement, not a
Cloudflare runtime selection. These additions belong only to projects selecting authentication.

When the server starts, RelKit rebuilds the instance from its options. It adds your Drizzle database
when the options set no `database`, and mounts the handler at `basePath`, `/api/auth` by default. Set
your own `database` in the Better Auth file to use another adapter; RelKit then needs no Drizzle service.
The session type that handlers read comes from this instance. The service exposes a stable `handler`;
it does not expose `auth.api` or a login function to call through `context.services`.

Add the environment fields to your existing configuration without replacing other settings:

Better Auth reads `BETTER_AUTH_SECRET` from the server process environment when it activates. The
example deliberately has no hard-coded secret or secret default. Keep the Docker setup's
`DATABASE_URL` and the stable auth values in your backend's untracked `.env.local`. Generate a
secret once if you have not completed the pre-setup:

```sh
openssl rand -base64 32
```

Set `BETTER_AUTH_SECRET` to that value and `BETTER_AUTH_URL` to your backend origin, locally
`http://127.0.0.1:3000`. Keep these fields in the existing `src/platform/env.ts` when the app
imports its environment instead of declaring it inline. SQLite apps retain `DATABASE_PATH`
instead of the PostgreSQL `DATABASE_URL` field.

Store a stable, strong secret in your deployment's secret manager; use the same value across replicas
and restarts. Do not regenerate it on every startup. Never put it in a browser bundle, a public
environment variable, source control, logs, or a copied example configuration.

The Better Auth file is plain Better Auth, not an `({ env })` factory. Declaring a field in `defineEnv`
validates the RelKit environment, and the server refuses to start without either value; it does not
inject parsed values into the file or replace `process.env`. The URL fallback in the file only serves
`relkit check`, which imports the file without your environment. The secret uses Better Auth's native
process-environment lookup. A test harness `env` override alone does not set that
process value; see [Testing](/docs/modules/auth/testing).

## Reach the auth endpoints

RelKit mounts the handler at `/api/auth` and preserves Better Auth's native responses, including
cookies; you add no route file. Pass `mount: false` to `defineBetterAuthService` to mount it yourself
with a raw `ALL` route instead. To require a session on an application route, set `auth: "required"`
on that route; see [Protect routes](/docs/modules/auth/protect-routes) for the check and authorization
rules.

You do not call `activateBetterAuthService` in normal application startup. Calling the service's
handler before the server activates it returns HTTP `503`; importing the service is not a standalone
auth server.

## Know which settings RelKit owns

| Setting                       | Owner and behavior                                                            |
| ----------------------------- | ----------------------------------------------------------------------------- |
| `database`                    | Yours to set; when unset, RelKit adds the Drizzle service's adapter           |
| `basePath`                    | Yours to set; RelKit mounts the handler there, `/api/auth` by default         |
| `baseURL`                     | Your public backend origin; configure it for each environment                 |
| `secret`, native auth options | Better Auth settings; this example uses its environment lookup for the secret |
| Connection disposal           | The Drizzle service's `dispose` callback, when RelKit adds the adapter        |

Better Auth writes through the native adapter, bypassing RelKit portable CRUD, generated Zod parsers,
and operation overrides. Do not use a table override as an auth policy or expose credential/session
tables through generic CRUD routes. See [Database integration](/docs/modules/database/better-auth).

Run `bun run check` and `bun run typecheck`, then verify a real sign-up and protected request using
[Your first auth flow](/guides/auth/email-password-sign-in). Continue with [Customization](/docs/modules/auth/customization)
before exposing a deployment to users.
