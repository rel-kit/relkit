Use `defineBetterAuthService` to add Better Auth credentials, accounts, and sessions to your application. RelKit discovers it, activates
the application's Drizzle connection first, and passes that native client to Better Auth's Drizzle
adapter. Better Auth handles credentials, accounts, sessions, and its HTTP protocol.

The current integration uses the default Drizzle service, one Better Auth service, and one
filesystem `ALL` catch-all mount for that auth handler. Do not construct a second connection for auth
or register the descriptor as a member of an ordinary `defineService`.

## Pre-setup

Use [authentication setup](/docs/modules/auth#pre-setup) to start local Docker PostgreSQL,
declare the database/auth fields with `defineEnv`, and supply a stable secret before startup.
If you completed that scaffold, skip installation below and customize the existing files.
Existing SQLite/MySQL applications keep their dialect and applied migration history.

### Scaffold the auth baseline

```sh title="Terminal — application root"
bun run relkit add auth --adapter better-auth --database-dialect postgresql
```

This creates the Better Auth file `src/services/auth/better-auth.ts` and its service
`src/services/auth/service.ts`, merges auth environment declarations, and installs the selected adapter, native SDKs,
declaration peers and repairs. It reuses the existing Drizzle service or creates one when absent.
`--database-dialect` must match an existing database; when none exists, it chooses the new dialect.

For an existing database, the scaffold adds `schema/auth.ts` and exports its tables from the
schema index. Review those additions, preserving business tables and applied migrations.
Existing auth table names cause a collision instead of being overwritten. The scaffold does not run migrations,
generate a secret, or protect business routes. Configure those before accepting sign-ins.

Run this once when the app has no auth service. If it already exists, edit its Better Auth file.
With `--no-install`, run `bun install` and `bun run check` before continuing. See the
[auth command reference](/docs/api/cli#relkit-add-auth) and
[complete sign-in guide](/guides/auth/email-password-sign-in).

Better Auth reads `BETTER_AUTH_SECRET` from the server process environment when it activates. The
example deliberately has no hard-coded secret or secret default. Keep the Docker setup's
`DATABASE_URL` and the stable auth values in your backend's untracked `.env.local`. Generate a
secret once if you have not completed the pre-setup:

```sh
openssl rand -base64 32
```

Set `BETTER_AUTH_SECRET` to that value and `BETTER_AUTH_URL` to your backend origin, locally
`http://127.0.0.1:3000`. Keep these fields in the existing `src/platform/env.ts` when the app
imports its environment instead of declaring it inline. SQLite apps retain `DATABASE_PATH`
instead of the PostgreSQL `DATABASE_URL` field.

Store a stable, strong secret in your deployment's secret manager; use the same value across replicas
and restarts. Do not regenerate it on every startup. Never put it in a browser bundle, a public
environment variable, source control, logs, or a copied example configuration.

The Better Auth file is plain Better Auth, not an `({ env })` factory. Declaring a field in `defineEnv`
validates the RelKit environment, and the server refuses to start without either value; it does not
inject parsed values into the file or replace `process.env`. The URL fallback in the file only serves
`relkit check`, which imports the file without your environment. The secret uses Better Auth's native
process-environment lookup. A test harness `env` override alone does not set that
process value; see [Testing](/docs/modules/auth/testing).

## Reach the auth endpoints

RelKit mounts the handler at `/api/auth` and preserves Better Auth's native responses, including
cookies; you add no route file. Pass `mount: false` to `defineBetterAuthService` to mount it yourself
with a raw `ALL` route instead. To require a session on an application route, set `auth: "required"`
on that route; see [Protect routes](/docs/modules/auth/protect-routes) for the check and authorization
rules.

You do not call `activateBetterAuthService` in normal application startup. Calling the service's
handler before the server activates it returns HTTP `503`; importing the service is not a standalone
auth server.

## Know which settings RelKit owns

| Setting                       | Owner and behavior                                                            |
| ----------------------------- | ----------------------------------------------------------------------------- |
| `database`                    | Yours to set; when unset, RelKit adds the Drizzle service's adapter           |
| `basePath`                    | Yours to set; RelKit mounts the handler there, `/api/auth` by default         |
| `baseURL`                     | Your public backend origin; configure it for each environment                 |
| `secret`, native auth options | Better Auth settings; this example uses its environment lookup for the secret |
| Connection disposal           | The Drizzle service's `dispose` callback, when RelKit adds the adapter        |

Better Auth writes through the native adapter, bypassing RelKit portable CRUD, generated Zod parsers,
and operation overrides. Do not use a table override as an auth policy or expose credential/session
tables through generic CRUD routes. See [Database integration](/docs/modules/database/better-auth).

## Remove the account issuer column

RelKit installs Better Auth 1.7.7, the first release without the advisories `npm audit` reports for
1.7.1. Better Auth 1.7.0 to 1.7.2 required an `issuer` column on the `account` table and a unique
index on `issuer` and `accountId`, and projects created with Better Auth 1.7.1 declare both. From
1.7.3, Better Auth identifies an account by `providerId` and `accountId` again, never writes
`issuer`, and checks the Drizzle schema when it starts. With the old column, authentication does
not start and the server prints:

```txt title="Terminal"
RELKIT_AUTH_SCHEMA_MISMATCH: The database schema does not match the installed Better Auth release, so every sign-up and sign-in would fail.
  Column account.issuer is required, but Better Auth 1.7.3 and later never write it: remove it and the index on issuer and accountId.
  next: Run `relkit migrate --write` (or remove `issuer` and the index on it from the account table by hand), then `db:generate` and `db:migrate`.
  docs: https://relkit.dev/docs/errors/relkit-auth-schema-mismatch
```

No account, user or session is lost: Better Auth 1.7.3 and later never read `issuer`, and the other
columns stay as they are. To upgrade a project:

1. Install `better-auth@1.7.7` together with the RelKit packages that require it. RelKit checks the
   installed version and names it when it differs.
2. Check that no two accounts share a provider and account ID, which Better Auth 1.7.3 and later
   reject. The [migration guide](/guides/migrate/relkit-0-9#better-auth-account-issuer) has the
   query.

3. Change the schema file. `relkit migrate` previews the change and `relkit migrate --write` applies
   it; to edit by hand, remove the column, the index and the imports only the index used. In
   `src/services/database/schema/auth.ts` of a PostgreSQL project:

   ```diff title="src/services/database/schema/auth.ts"
   -import { boolean, pgTable, text, timestamp, uniqueIndex } from "drizzle-orm/pg-core";
   +import { boolean, pgTable, text, timestamp } from "drizzle-orm/pg-core";
   @@
    export const account = pgTable(
      "account",
      {
        id: text().primaryKey(),
        accountId: text().notNull(),
   -    issuer: text().notNull(),
        providerId: text().notNull(),
   @@
        ...timestamps,
      },
   -  (table) => [uniqueIndex("account_issuer_account_id").on(table.issuer, table.accountId)],
    );
   ```

   Keep `uniqueIndex` imported when other tables, such as the organization plugin's `member`, still
   use it. SQLite and MySQL schemas change the same way.

4. Generate the migration with `bun run db:generate` (`npm run db:generate` on npm) and review it.
   Drizzle drops the `account_issuer_account_id` index first and the `issuer` column second.

5. Apply it with `bun run db:migrate` (`relkit db migrate`) in every environment before the new
   release serves requests, then sign up a new user and sign in with an existing one.

To keep the column's values, make it nullable instead (`issuer: text()`) and keep the index:
Better Auth accepts a nullable column it does not write, and the generated migration only drops
`NOT NULL`. Setting `advanced.database.validateSchema: false` in the Better Auth file turns the
startup check off; inserts into a table with a required `issuer` column still fail.

## Read the authentication operations in the API reference

The served document at `/_relkit/v1/openapi.json` and the API reference include the mounted Better
Auth operations under the Authentication tag. Better Auth generates them, and RelKit corrects what
it can verify from Better Auth's source: `nullable: true` becomes OpenAPI 3.1 nullability, so a new
user's `image` validates as `null`. The corrections also fix the success answers of
`organization/delete`, `organization/has-permission`, `organization/check-slug`,
`organization/list-invitations` and `organization/list-members`. Every operation that takes a body
also declares 413 and 415.

### Read an authentication error

Better Auth answers every request under its mount, and its errors keep Better Auth's format. They
are not [Problem Details](/docs/modules/http/responses#read-an-error-response):

```json
{ "message": "Invalid email or password", "code": "INVALID_EMAIL_OR_PASSWORD" }
```

- `message` is text for people. `code` is Better Auth's code for the error; branch on it. A few
  errors carry `message` alone.
- A validation failure has the code `VALIDATION_ERROR` and adds `issues`, one entry per failing
  field with its `path` and `message`.
- Some errors have no body, such as the 401 of an organization endpoint called without a session.
  Read the status first.

RelKit does not convert these errors, because Better Auth's own client reads this format. The
reference declares it as the `BetterAuthError` schema on every error response of these operations.

RelKit answers two cases itself, before Better Auth runs, and those are Problem Details:

- State-changing operations, such as `POST /api/auth/organization/set-active`, answer 403 with
  `application/problem+json` (code `origin-denied` or `csrf-denied`) when the request comes from
  another origin and transport security is on. The reference lists both media types for the 403 of
  these operations.
- A body over the server's limit answers 413 with the code `payload-too-large`.

The reference lists an operation only when your configuration serves it. An endpoint of a plugin
you did not add is absent, and so is `POST /api/auth/get-session` unless you set
`session.deferSessionRefresh`, because Better Auth answers 405 to it otherwise. An endpoint that is
served is listed whether or not your application calls it.

These differences between the reference and the server remain:

- Some operations declare no success answer, such as `organization/leave`,
  `organization/cancel-invitation` and `organization/get-active-member-role`.
- A failed `organization/set-active` for an unknown organization clears the active organization;
  this is Better Auth's behavior.

Run `bun run check` and `bun run typecheck`, then verify a real sign-up and protected request using
[Your first auth flow](/guides/auth/email-password-sign-in). Continue with [Customization](/docs/modules/auth/customization)
before exposing a deployment to users.
