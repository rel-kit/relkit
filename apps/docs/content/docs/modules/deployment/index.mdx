Deployment makes a checked application run in its target environment. Begin with local Docker
for development dependencies and container verification, then choose how to host the built server
and supply its production resources.

## Pre-setup

Complete each module's local configuration before building: [database](/docs/modules/database#pre-setup),
[auth](/docs/modules/auth#pre-setup), [storage](/docs/modules/storage#pre-setup),
[cache](/docs/modules/caching#pre-setup), [jobs](/docs/modules/jobs#pre-setup), and
[realtime](/docs/modules/realtime#pre-setup). Keep required application values in `defineEnv`
and connect that descriptor through `defineApp({ env })`.

From the backend root, verify the application before choosing a deployment target:

```sh title="Terminal — application root"
bun run check
bun run typecheck
bun run test
bun run build
```

These commands create no cloud resources. A production server receives secrets from its process
environment; the build does not embed `.env` values. Preserve application state, database migrations,
and immutable worker versions across releases.

## Deploy targets and engines

`relkit deploy init <target>` writes a target's configuration. A target uses Pulumi only when a
maintained Pulumi provider exists for it; otherwise RelKit generates the platform's own
configuration and deploys with the platform's CLI, with no Pulumi program or state.

| Target     | Engine                                                                                  | What `relkit deploy init` writes                                                               | Status                                                |
| ---------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| Railway    | Container image, deployed with the Railway CLI                                          | `railway.json`, `Dockerfile`, `.dockerignore`, a GitHub Actions workflow                       | Labs; [guide](/docs/modules/deployment/railway)       |
| AWS        | Pulumi, through `@relkit/pulumi` and `@relkit/aws`                                      | A Pulumi project and stack (`relkit deploy init aws`)                                          | Labs; [guide](/docs/modules/deployment/aws)           |
| Vercel     | Platform configuration (`vercel.json`), one Node function, deployed with the Vercel CLI | `vercel.json`, the function entry `api/relkit.mjs`, `.vercelignore`, a GitHub Actions workflow | Labs; [guide](/docs/modules/deployment/vercel)        |
| Cloudflare | Platform configuration (`wrangler.jsonc`), the Workers bundle                           | Not available yet                                                                              | Coming after the Workers adapter                      |
| Any host   | The image `relkit build` emits                                                          | Nothing: build and run the image yourself                                                      | [Local Docker](/docs/modules/deployment/local-docker) |

`relkit deploy init` without a target keeps initializing the AWS Pulumi stack.

## Supported providers

| Role                                | Supported path                                                         | What RelKit manages                                                                                                                                                                  |
| ----------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Local development services          | Docker recipes for Redis, MinIO, Inngest, Trigger.dev, and Effect MQ   | Graph-required containers, readiness, connection values, and persistent volumes; [coverage](/docs/modules/integrations/local-docker#supported-local-services)                        |
| Self-hosted application             | Built Bun server or generated Docker image                             | Portable build output; you provide the host, process/container supervisor, TLS, and resource connections                                                                             |
| Container platform host             | **Railway**, through `relkit deploy init railway`                      | Generated `railway.json`, Dockerfile and deploy workflow; Railway Postgres as the durable backend; [Railway guide](/docs/modules/deployment/railway)                                 |
| Function platform host              | **Vercel**, through `relkit deploy init vercel`                        | Generated `vercel.json`, function entry and deploy workflow; Vercel Cron for schedules; an external Postgres as the durable backend; [Vercel guide](/docs/modules/deployment/vercel) |
| Cloud application host              | **AWS**, through `@relkit/aws`                                         | ECS/Fargate, networking, load balancer, workload access, and CloudWatch stdout; [AWS setup](/docs/modules/deployment/aws)                                                            |
| Infrastructure engine               | **Pulumi**, through `@relkit/pulumi`                                   | Stack configuration, preview, apply, outputs, refresh, and destroy                                                                                                                   |
| Infrastructure-owned resources      | AWS wrappers for supported S3 and Redis/Valkey resources               | Resource lifecycle and access, separately from the application host                                                                                                                  |
| Connected file/cache resources      | S3-compatible storage, Redis, Cloudflare R2 and KV                     | Runtime connections to existing resources; [provider configuration](/docs/modules/deployment/providers)                                                                              |
| Native durable tasks                | Inngest, Trigger.dev, Effect MQ                                        | Provider-specific worker publication, schedules, and supported run semantics; [job deployment](/docs/modules/jobs/deployment)                                                        |
| Application data and authentication | Drizzle with PostgreSQL, MySQL, or SQLite; Better Auth on that service | Application connection and auth activation; you own database hosting, migrations, and backups                                                                                        |
| Models and telemetry                | Selected LangChain model SDKs, Sentry, OTLP                            | Selected runtime integration; no implicit provisioning or model account                                                                                                              |

Railway, Vercel and AWS are the deploy targets today. The Cloudflare package provides **R2/KV runtime
adapters**, not Workers application deployment. There are no built-in Azure or Google Cloud host
integrations yet. A platform that runs the built server or image can be used through
the self-hosted path; that is separate from `relkit deploy` support.

Pulumi's cloud, local, and object-storage state backends store stack state; they do not add
application hosts. The native job packages also publish deployment hooks for their workers,
not alternative infrastructure engines selected by `defineApp.deployment.engine`.

## Move from local to production deliberately

`docker(adapter)` is a development selection. It does not create cloud infrastructure or make
a loopback connection reachable from production. Use configured connected adapters or supported
infrastructure wrappers for release builds, and keep descriptor IDs and profile names consistent.
Verify the real provider's behavior, credentials, network access, persistence, and migrations before
accepting production traffic.

Cloud/deployment creation flags remain unavailable for new starters. Add the selected tooling to
an existing app following [AWS setup](/docs/modules/deployment/aws#install-deployment-tooling-for-an-existing-app).
