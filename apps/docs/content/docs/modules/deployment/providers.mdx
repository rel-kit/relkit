Choose runtime resources independently from the application host. An AWS-hosted app can use an
existing Redis service or Cloudflare R2; selecting those adapters does not make the deployment
stack own their lifecycle.

## Pre-setup

Begin with [local Docker configuration](/docs/modules/integrations#pre-setup) and passing module
checks. Before releasing, obtain the target resource's connection values and store secrets in
your deployment's runtime environment. Keep stable descriptor IDs and profile names when changing
their provider. Verify supported operations: a connected provider is not automatically equivalent
to the one used during development.

Application fields belong in `defineEnv`. The named `binding` references below describe provider
connections; they are not extra `context.env` fields. Keep your existing environment contract,
server settings, and application identity when merging either example.

## Realtime and agent checkpoints

Use the [Redis realtime configuration](/docs/modules/realtime/providers) with a reachable secret
connection binding in production, and configure `agent-state` separately for agents. Confirm Redis
persistence and shared fanout across replicas; local filesystem profiles require one shared,
appropriately managed state location and are not a replacement for distributed provider semantics.

## Durable job providers

| Provider | Local default | Deployment guidance |
| --- | --- | --- |
| Inngest | `docker(inngest())` | [Inngest setup](/docs/modules/jobs/providers/inngest): connected credentials, native worker registration, and capability evidence |
| Trigger.dev | `docker(trigger())` | [Trigger.dev setup](/docs/modules/jobs/providers/trigger): target runtime, immutable worker publication, and provider connection |
| Effect MQ | `docker(effectMq())` | [Effect MQ setup](/docs/modules/jobs/providers/effect-mq): PostgreSQL-backed native execution and worker lifecycle |

Follow [job deployment](/docs/modules/jobs/deployment) to publish workers, verify readiness, and
activate schedules. Keep previous worker generations while they own accepted runs. Application
events use the [filesystem provider](/docs/modules/events#pre-setup); persist their state explicitly.

## Database and authentication

The [database service](/docs/modules/database/define) connects PostgreSQL, MySQL, or SQLite.
RELKIT does not provision an application database through `defineApp`. Supply its connection via
`defineEnv`, migrate once before rollout, and keep backups and connection/network policy with the
database owner. The Docker PostgreSQL walkthrough is development setup, not a managed cloud database.

[Better Auth](/docs/modules/auth#pre-setup) shares that service. Use the public production origin
for `BETTER_AUTH_URL`, a stable secret across replicas, and reviewed cookie/origin policy. Keep
credentials and session tables out of generated public CRUD endpoints.

## Models and telemetry

Selected [model SDKs](/docs/modules/ai/agents#choose-a-model) own model credentials and availability.
Sentry and OTLP are independent [telemetry exporters](/docs/modules/operations/observability),
configured with named endpoint/secret bindings. AWS hosting supplies CloudWatch stdout routing;
it does not create a model account, Sentry project, or OTLP service.

## Verify the release configuration

Run `bun run check`, `bun run typecheck`, and `bun run build` after changing bindings. These
validate the application and selected contracts; they do not prove remote credentials or network
access. Verify a real read/write and applicable rejection path against your intended provider in
an isolated environment before accepting traffic. Follow [AWS deployment](/docs/modules/deployment/aws)
only when that host is selected.
