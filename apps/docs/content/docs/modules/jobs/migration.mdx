Preserve durable job and task identities when changing application source or provider configuration. Preserve the existing public job ID, task ID, version, input schema, output schema, dedupe scope, schedule identity, and client fingerprint unless the change is intentional.

This is a one-release compatibility window. Legacy function-target definitions, `.enqueue()` producers,
and the deprecated `profile` spelling remain available only when explicitly enabled; new code must use a
task-first definition and `service` selection. Use a compatible release cohort before changing the
application graph; packages have independent versions, so follow the selected owner's installation
requirements rather than assigning one version number to every RELKIT package.

The migration helper is exposed from the jobs package; run it against the previous and next snapshots before
activation. It reports identity, binding, schema, history, schedule, dedupe, and client-fingerprint changes.

Diagnostics flag pinned/default-derived ID changes, implicit-to-explicit binding changes, task version or schema incompatibility, history and schedule changes, dedupe changes, and client fingerprint changes. Legacy aliases and function-target definitions must be explicit during the migration window; the compiler does not silently rewrite them.

Roll out a compatible worker first, register the task-first definition, wait for readiness, then activate new triggers. Keep the old definition and worker generation until historical runs are terminal. If the input or output contract is incompatible, use a new task version or a new public job ID and document the boundary.

Provider retention, native listing, durable sleep, schedule recovery, and cancellation limits are variant-specific.
Check the [provider comparison](/docs/modules/jobs/providers) and deployment evidence before relying on them; unsupported
or not-tested capabilities are not emulated by the RELKIT runtime.
