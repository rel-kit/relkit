Use Inngest to give RELKIT tasks a durable execution path. You will prepare an Orders CSV from
validated order rows, submit the job, and confirm both registration and completion. You need
Bun 1.3.10 and a running Docker daemon. Start in a parent directory where `relkit-inngest`
does not already exist. The task returns CSV text; it does not write a file or query a database.

## Set up Inngest locally

`inngest-docker` runs Inngest's local server, PostgreSQL, Redis, and a RELKIT worker. You do
not need an Inngest Cloud account, an API key, or a separate `inngest dev` process for this
profile. `bun run relkit local up --detach` creates provider credentials and connects the
worker to the Inngest server. The generated config above is the connection point; do not
paste the generated signing or event keys into source files. Start the RELKIT backend with
`bun run dev` after the local services are healthy.

To find Inngest's dashboard address, inspect the mapped port and open the `127.0.0.1` URL
for the container ending in `service-inngest`. The host port is allocated dynamically, so
`8288` is the **container** port, not necessarily the port to enter in your browser.

```sh title="Terminal — relkit-inngest"
docker ps --filter name=service-inngest --format '{{.Names}} {{.Ports}}'
```

In the dashboard, **Functions** must list the Orders export function after the backend
starts. This historical screenshot records a fresh flat-layout local-source fixture; its
native registration evidence predates the grouped move and does not certify a new creation tuple.

## Start and submit a run

Check the app, start Inngest and its local dependencies, then leave the development server
running. Start the provider **before** the backend so the worker can connect.

```sh title="Terminal — relkit-inngest"
bun run check
bun run typecheck
bun run relkit local up --detach
bun run relkit local status
bun run dev
```

In a second terminal, first prove that RELKIT registered `exportOrders` with task
`orders.export-orders` on the `default` profile. Then trigger the job. The trigger response
is an acceptance receipt, not proof of execution. Copy its `runId` into the final command.

```sh title="Second terminal — relkit-inngest"
bun run relkit jobs capabilities
bun run relkit --json jobs list
bun run relkit --json jobs trigger --job exportOrders --input-file examples/export-orders.json --operation-id orders-csv-1
bun run relkit jobs runs get --run-id <runId>
```

Repeat the read until `run.status` is `completed`. The run moves from the `event:` receipt
to an Inngest-native run ID. In a local-source check, the worker logged `Orders CSV prepared`
with `orderCount: 2` and `totalCents: 2100`, and the native run completed. The current
Inngest run lookup may report `resultAvailability: "void"` even when the task returns CSV;
use the worker log to verify totals and do not rely on this lookup to download the CSV.
If the run remains pending, inspect `bun run relkit local status` and the backend terminal.

Open **Runs** in the same Inngest dashboard. The completed row below is the native run of
the registered Orders export function from that fresh app, not merely a RELKIT acceptance
receipt. Match its function name and run ID to your own run when repeating the steps.

![Inngest local Runs page showing a completed Orders export run](/jobs-inngest-completed.png)

The current Inngest path supports UTC cron schedules and durable sleep. Interval schedules,
arbitrary timezones, overlap policies, and historical-build resume are not established by
this profile. The documented limits are 1 MiB each for input and output, 64 KiB for a
progress item, and 100 items for run listing. Check `jobs capabilities` for the selected
environment before using an optional operation. Continue with [job clients](/docs/modules/jobs/clients)
to trigger and observe runs from application code.
