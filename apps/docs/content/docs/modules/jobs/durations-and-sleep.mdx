Pause task execution through the provider's durable sleep capability when the selected provider supports it.

<Callout type="note" title="Before you begin" icon="clipboard-check">
  Use an existing [task/job with its selected provider installed and
  bound](/docs/modules/jobs/quickstart) before running this example. Core task declarations do not
  install the provider's native SDK.
</Callout>

Set `maxDuration` or `maxElapsed` on the task. `maxDuration` is the longest active time of one attempt;
time asleep or waiting to retry does not count. `maxElapsed` is the longest total time from the
acceptance of a run, with delays, sleep and retries.

The local backend from `@relkit/local` enforces both. An attempt that reaches `maxDuration` fails with
`RELKIT_TIMEOUT` and is retried while the task's `retry` allows it. A run that reaches `maxElapsed` is
not retried. A run stopped by either limit ends with the status `timed-out`.

The Inngest, Trigger.dev, Effect MQ and Postgres backends do not enforce these limits. `relkit check`
reports each such task and limit with the warning
[`RELKIT_JOB_TASK_OPTION_UNSUPPORTED`](/docs/errors/relkit-job-task-option-unsupported), and the
server logs the same warning when it starts. On those backends, enforce the limit in the handler.

Durable sleep records a continuation with the provider. A durable task calls
`context.sleep("1 hour", { key: "wait-before-notifying" })`; it must not use `setTimeout` in a worker
process because a restart would lose the continuation.

Providers differ. Inngest currently supports durable sleep for its supported path. Effect MQ does not advertise durable sleep. Trigger Docker does not claim checkpointed sleep. Check capabilities before relying on a long pause.

Use UTC for provider-native schedules. A task that needs a local business timezone should calculate the next instant explicitly and persist the business timezone in its input.
