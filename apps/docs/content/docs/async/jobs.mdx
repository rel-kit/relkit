A job separates accepting work from executing it. Enqueue returns after the provider accepts validated input;
the target may run later, on another worker, and more than once after an uncertain acknowledgement. Use jobs
for slow or retryable work that should not hold an HTTP request open.

## Implement and verify a job flow

<Steps>
  <Step>
    ### Keep target input durable

    Enqueue identifiers and immutable facts, not live request objects, open files, provider clients, or
    closures. The payload must remain valid JSON and may be stored beyond the originating process.

  </Step>
  <Step>
    ### Enqueue after the owning state transition

    Call `context.jobs.<name>.enqueue(input)`. Successful enqueue means accepted for delivery, not completed.
    Return an HTTP `202` only when that distinction is part of the route contract.

  </Step>
  <Step>
    ### Assert the fake queue

    In a unit test, provide deterministic job clients through `invokeFunction`, call the function, and inspect
    the captured payload. This proves authorization and input without a worker or cloud credentials.

  </Step>
  <Step>
    ### Exercise worker behavior

    Use the job testing harness for success, retryable error, terminal error, timeout, duplicate delivery, and
    recovery after restart. Advance the test clock rather than sleeping.

    ```sh title="Terminal — relkit-orders"
    bun run check
    bun run test:integration
    ```

  </Step>
</Steps>

## Delivery and failure semantics

Durable providers normally deliver at least once. A worker can finish the side effect and crash before
acknowledgement, causing another attempt. Idempotency suppresses duplicate job admission for the configured
key and retention window; the target must still make external side effects idempotent when exactly-once
behavior matters.

Declared errors use their retry metadata. Unexpected defects follow the job's bounded retry policy and stay
redacted. After `maxAttempts`, the provider records terminal failure according to its implementation; inspect
the job attempt and cause in diagnostics rather than silently enqueueing forever.

<Callout type="warn" title="Concurrency is not ordering">
  A concurrency limit bounds simultaneous executions. It does not guarantee FIFO completion,
  serialize jobs with the same domain ID, or prevent duplicates.
</Callout>
