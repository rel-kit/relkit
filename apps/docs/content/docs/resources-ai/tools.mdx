A tool is a model-facing view of an existing function. It adds a stable tool ID, description, side-effect
classification, approval policy, timeout, and optional hooks; it does not own another business handler. The
function's input, output, and declared errors remain the executable contract.

`asTool` keeps the tool close to its target. Use `defineTool({ target, ... })` when model-facing metadata belongs
in a separate module. The description should tell the model when to call the tool and what it returns without
promising behavior the function does not implement.

## Classify side effects

| Value      | Meaning                                                 | Typical approval                                   |
| ---------- | ------------------------------------------------------- | -------------------------------------------------- |
| `none`     | Pure calculation with no external reads or writes       | Often `never`                                      |
| `read`     | Reads application or external state                     | `never` only when disclosure is already authorized |
| `write`    | Mutates application state                               | `on-write` or `always`                             |
| `external` | Causes an external action such as sending or purchasing | Usually `always`                                   |

Classification is security metadata, not documentation decoration. Marking a mutating operation as `read`
can bypass an intended approval boundary.

## Add a tool to an agent

<Steps>
  <Step>
    ### Start from a tested function

    Verify input, output, errors, authorization, and idempotency without a model. A tool cannot make an unsafe
    target safe.

  </Step>
  <Step>
    ### Add bounded metadata

    Choose a stable ID, precise description, truthful side effect, approval policy, and short timeout. Use hooks
    only for model-specific input/output shaping that preserves the function schema.

  </Step>
  <Step>
    ### Allowlist it explicitly

    Add the descriptor to one agent's `tools` array. Discovering a tool in source does not grant every agent
    permission to execute it.

  </Step>
  <Step>
    ### Test with a scripted model

    Use the AI SDK v7 test-backed harness to produce a known tool call. Assert parsed input, target result,
    tool-call count, timeout, and that an unlisted tool is rejected. No provider key or network call is needed.

  </Step>
</Steps>

Tool calls enter the common function engine, so validation, context, tracing, declared errors, and cancellation
remain consistent with HTTP and jobs. Directly calling the target handler would bypass those guarantees.
