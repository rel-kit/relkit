An agent combines validated input/output, instructions, model selection, an explicit tool allowlist, and hard
execution limits. It is appropriate when a model must decide among bounded steps. Use an ordinary function
when the workflow is deterministic; a model adds latency, cost, and nondeterminism.

The agent can call only `lookupOrder`. `maxSteps`, `maxToolCalls`, and `timeoutMs` bound loops and provider
latency. The output schema rejects prose or structure outside the application contract.

## Build an agent scenario

<Steps>
  <Step>
    ### Define success without a model

    Write the input and output schemas and test each tool target directly. Decide what the agent must return
    when an order is missing, a tool fails, approval is denied, or the model reaches a limit.

  </Step>
  <Step>
    ### Write narrow instructions

    State the task, tool-use conditions, prohibited actions, and output expectations. Do not put secrets in
    instructions; providers may retain or inspect prompts according to their service policy.

  </Step>
  <Step>
    ### Allowlist the minimum tools

    Include only tools required for this workflow. Read-only support should not receive cancellation, payment,
    or administration tools “for later.” Protected tools retain their approval policy.

  </Step>
  <Step>
    ### Test with scripted model output

    Use the AI SDK v7 `ai/test`-backed harness. Script a direct answer, one valid tool call, an unknown tool, a
    malformed argument, approval denial, and a loop that reaches the call limit. Assert final output and traced
    steps without network access.

  </Step>
</Steps>

## Configure a live provider

Bind an AI SDK adapter under `models` in `relkit.config.ts`. Reference its API key through `env.secret()`, set
an explicit default provider/model, and keep normal tests on the fake harness. A model name such as
`provider:model` selects an exact binding; omitting a model uses the configured default.

Live integration tests are opt-in because they can cost money, vary across provider releases, encounter rate
limits, and transmit prompt data outside the process. Mark them separately and set a spending limit at the
provider account.

## Operational failure modes

Handle provider timeout, rate limit, invalid structured output, tool failure, approval denial, and exhausted
limits as normal bounded outcomes. Trace model steps and tool calls with correlation and redaction, but do not
record secrets or complete sensitive prompts by default.

<Callout type="warn" title="A model is not an authorization system">
  Authenticate the caller and authorize tool targets in application code. Instructions and model
  reasoning do not replace access control.
</Callout>
