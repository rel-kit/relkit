This example uses the repository's `examples/commerce` application, which already contains an
Orders export task and a Docker-backed Inngest job binding. It is an optional extension after
the [Orders API tutorial](/docs/start/build-and-run), not a file replacement in your protected
`relkit-orders` app. You need Bun, repository dependencies, and Docker for a live provider run.

## 1. Define a task

A task owns durable execution. This one accepts order IDs, emits progress, and returns CSV text.
Its helper `exportOrderCsv` lives in the commerce example; if adapting the pattern to your app,
replace that helper with your own business operation and keep its schemas explicit.

<include cwd lang="ts" meta='title="examples/commerce/src/orders/tasks/export-orders.task.ts"'>
  ../../examples/commerce/src/orders/tasks/export-orders.task.ts
</include>

The task ID and version are stable compatibility identifiers. Change the version when the input or output contract is intentionally incompatible.

## 2. Expose a job

The job gives the task a public name and client policy. The HTTP route below is a separate
entry point; its handler accepts a run and returns `202`, not the CSV output.

  ../../examples/commerce/src/orders/jobs/export-orders.job.ts
</include>

<include cwd lang="ts" meta='title="examples/commerce/src/routes/orders/export/route.ts"'>

</include>

The commerce Orders service exports both the task and job. Its `relkit.config.ts` binds
`jobs.default` to `docker(inngest())`, so the compiler can check durable capabilities. When
adapting this to your own app, add a supported job binding before starting a run.

To scaffold the task-first job after creating the task, run:

```sh
bun run relkit add job "Export Orders" --service orders --target orders.export-orders-task
```

The `--target` value is the task ID. The generated job owns admission and client operations while
the task remains the unit of execution and compatibility.

For every job scaffolding flag, see the [CLI reference](/docs/operations/cli-reference).

## 3. Trigger and observe

The generated trigger receives `{ input, options }` and returns an accepted `RunHandle`. For example,
call `client.jobs.exportOrders.trigger({ input: { orderIds }, options: { operationId } })`, then read
`client.jobs.exportOrders.runs.get({ runId: accepted.runId })`. Keep the accepted `runId` and
`operationId`; a handle is an admission receipt, not the task output.

Use [job clients](/docs/jobs/clients) for the complete trigger/watch lifecycle and
[progress and streams](/docs/jobs/progress-and-streams) for live updates.

## 4. Run locally

```sh title="Terminal — examples/commerce"
bun run check
bun run typecheck
bun ../../packages/cli/dist/index.js local up --detach
bun ../../packages/cli/dist/index.js local status
```

Start `bun run dev` after the provider reports ready. In another terminal, submit a run:

```sh title="Second terminal — examples/commerce"
bun ../../packages/cli/dist/index.js jobs capabilities
curl -i -X POST http://127.0.0.1:4000/orders/export \
  -H 'content-type: application/json' \
  -d '{"orderIds":["order-1"]}'
```

Expect HTTP `202` and a `RunHandle` with a `runId`; read or watch that ID until completion.
The local provider is
selected by the project binding. Use `relkit local reset --dry-run` before clearing local state.

Run `bun run test` from `examples/commerce` before changing the task. A passing test checks
application behavior, while the Docker run checks the selected provider.
