---
title: Schedules
description: Run jobs on provider-backed schedules.
---

Schedules belong to jobs and use the same task input and admission rules as an on-demand trigger.

<include cwd lang="ts" meta='title="examples/commerce/src/orders/jobs/cleanup-orders.job.ts"'>
  ../../examples/commerce/src/orders/jobs/cleanup-orders.job.ts
</include>

Use `schedules`, an array of definitions with an explicit `id`, canonical `input`, and either a cron/timezone
pair or an interval. Schedule operations return a receipt with an operation ID; they do not pretend that a
provider accepted a write when its outcome is unknown.

Use an explicit job ID and keep schedule ownership in source control. `relkit jobs schedules list|get|upsert|pause|resume|delete` manages the registered definition; each write returns an operation ID that can be audited.

Schedules are provider-backed. Do not run a second process-local scheduler as a fallback: it can double-trigger work after a restart. Check `relkit jobs capabilities` for the selected provider's cron, interval, timezone, overlap, and misfire support. The current Inngest path supports UTC cron schedules; interval and richer misfire policies are not silently emulated.

Pausing a schedule prevents new admissions and does not cancel runs already accepted. Delete or change a schedule only after checking in-flight runs and the migration impact on dedupe keys.
