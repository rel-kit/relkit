---
title: Job clients
description: Trigger a public job, retain its run ID, and watch or control that run.
---

After [defining and binding a job](/docs/jobs/quickstart), run `relkit client pull` for the app's
typed contract. Only jobs with a `client` policy appear. Triggering one admits work; the returned
handle identifies a run and is **not** the completed result:

```ts title="In a client with generated job declarations"
const accepted = await client.jobs.exportOrders.trigger({
  input: { orderIds },
  options: { operationId },
});
const latest = await client.jobs.exportOrders.runs.get({ runId: accepted.runId });
```

Keep `accepted.runId` and `operationId` so a later page load or retry can inspect the same run.
The app must authorize the caller for this job; a typed client alone does not grant access.

## Watch one accepted run

`watchJobRun` uses the accepted run ID. This public API example subscribes to state changes,
connects once, and disposes the watcher when its caller is finished:

<include cwd lang="ts" meta='title="Watch an export run"'>
  ../../apps/docs/examples/jobs/watch-run.ts
</include>

Call the returned cleanup function when the component or request scope ends. Reconnection
resumes observation; it does not trigger a second run. Keep credentials on the server-side
boundary for private jobs.

Cancel and retry are explicit controls with `{ runId, operationId }`, allowing audit and recovery.
The server may process them asynchronously; read or watch until the requested state appears.
