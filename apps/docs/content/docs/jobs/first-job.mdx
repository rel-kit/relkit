Add a receipt job to an existing RELKIT app. The producer receives queue acceptance; the target runs
separately. These source-backed examples are typechecked with the documentation app.

The job owns retry, timeout, concurrency, scheduling, and admission idempotency policy. The function owns

## Add the producer

Declare the job under `dependencies.jobs`, await admission, and return only the acceptance data your caller
needs:

Expose this producer through the Receipts service when routes or other domains need it. Keep the worker
target private when nothing else calls it directly.

## Bind and verify the profile

The example selects job profile `queue`. Configure a compatible adapter at `defineApp({ job: { queue: … } })`,
or change the descriptor and `defaults.job` together. Binding connection names are private to that adapter;
they do not become handler-visible environment fields.

No `RELKIT_ENV` value installs a hidden queue. A full `dev`, build, or deployment run must resolve the
selected integration. The bundled harness below remains credential-free and is the fastest proof of worker
behavior.

## Test admission and execution

The repository harness enqueues, inspects, drains, restarts, and advances time without sleeping:

<include cwd lang="ts" meta='title="packages/testing/jobs.test.ts"'>
  ../../packages/testing/jobs.test.ts
</include>

Run the smallest checks from your application root:

```sh
bun test
bun run check
bun run typecheck
```

Assert acceptance before draining, then assert the eventual side effect or result. Add restart and
redelivery cases for non-repeatable work. Passing the harness does not prove a production integration's
deduplication, dead-letter, or schedule guarantees; run that integration's contract tests separately.
