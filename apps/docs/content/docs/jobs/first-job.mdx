Add a receipt job to an existing RELKIT app. One function will accept the request; a worker will write
a receipt JSON object. You will test that acceptance happens before execution and that local duplicate
protection survives a restart.

Use an installed app with the standard `@app/*` alias. Follow [Create an app](/docs/start/create-an-app)
if needed. The commerce example already has the receipt target, job, bucket, and provider configuration:
inspect those files instead of replacing them. The enqueue function below is kept as an executable test
fixture in that example and must be placed under `src/` to become an application operation.

## Prepare the queue and bucket

Follow [Define a job](/docs/jobs/define#bind-a-jobs-provider) to merge the `jobs.default` binding
and jobs environment fields into your application. Set `defaults.job` to `"default"`.

The target also uses `assets.objects` from the Assets domain. If your app does not have that domain yet,
follow [Storage setup](/docs/storage/first-upload) through its provider, environment, bucket, function,
and service setup. You do not need its upload route for this job. The commerce bucket accepts JSON:

<include cwd lang="ts" meta='title="src/assets/buckets/assets.bucket.ts"'>
  ../../examples/commerce/src/assets/buckets/assets.bucket.ts
</include>

Keep unrelated configuration intact. The automated test below supplies local fakes and needs no cloud
credentials. For an interactive run, `RELKIT_ENV=test` also selects local providers.

It returns a receipt identifier, not a mail delivery confirmation. The job worker validates that output;
the enqueue caller does not receive it.

## Test admission, execution, and restart

Add `tests/jobs.test.ts` using the executable commerce test. Change its `queueReceipt` import from the
test fixture path to `@app/receipts/functions/queue-receipt.function.js` in your app:

<include cwd lang="ts" meta='title="tests/jobs.test.ts"'>
  ../../examples/commerce/tests/jobs.test.ts
</include>

The generic harness target type requires a type-only cast for this dependency-bearing descriptor; the
explicit bucket client supplies the dependency at runtime. The non-null assertions read optional fields
that this particular job defines. Copy the job's policy explicitly: `createTestJob` takes a target and
options, not the whole descriptor, and does not start its schedules.

From your application's root:

```sh
bun test tests/jobs.test.ts
bun run check
bun run typecheck
```

The test asserts acceptance with no stored file, drains the worker, checks the receipt, restarts the
local queue, and proves that the same key reuses the completed instance. It closes both fakes afterward.
This proves the local provider contract, not production SQS deduplication.

## Inspect an interactive run

Start the app with local providers:

```sh
RELKIT_ENV=test bun run dev
```

Open the Inspector at the URL printed by the development command, normally `http://localhost:3210`.
Find the public `receipts.queue-receipt` function and choose **Invoke locally** with:

```json
{ "orderId": "order-1", "receiptKey": "receipts/order-1.json" }
```

Expect `accepted: true` and an `instanceId`, not a `receiptId`. The running job worker processes accepted
work independently. Inspect `receipts.send-job` in Jobs and `receipts/order-1.json` in the Assets bucket;
the stored JSON should contain `orderId: "order-1"`. Calling `sendReceipt` directly only tests the function,
not queue delivery.

Run the producer again with the same input during the retention window: the local queue should reuse
the instance. Use a new order ID **and** a new receipt key to demonstrate distinct work without overwriting
the previous receipt. For failure cases, continue with [Retries and delivery](/docs/jobs/retries); for
HTTP admission, target the public producer from an [HTTP route](/docs/http/define).
