Choose the domain that owns the behavior, then the kind of file. For example, an order lookup belongs to
Orders whether it is reached from HTTP, another function, or an AI model. Its implementation stays in
`src/services/orders/functions/`; the entry points reference it.

## The placement map

The paths below are patterns, not files you must create in every domain. Replace `orders` with the owner.

Default-export each ordinary descriptor from its own file, following its capability's guide. Route files
are different: they export named HTTP methods. Plain helper modules are ordinary TypeScript; they do not
need a RelKit descriptor or their own service.

## One selected service root

New applications place boundaries at `src/services/<name>/service.ts`. Existing flat
applications keep `src/<name>/service.ts`, and `relkit add` preserves the detected layout.
Choose one root for the whole application, including Database and Auth. A directory alone,
an empty `services/` directory, or a folder containing only helpers does not select a layout.
Discovery uses authored service and descriptor evidence.

Each service is an immediate child of the selected root. Every descriptor belongs beneath
exactly one boundary. Nested boundaries, mixed flat/grouped services, missing boundaries,
and an aggregate `src/services/service.ts` are structural errors. A source-only move keeps
logical IDs, URLs, exposure, resource ownership and policies stable. Use the
[optional migration guide](/docs/service/migration) for coordinated moves and rollback.

## Imports follow the boundary

Service implementation files can import their own files, Platform, and another service's
public `service.ts` boundary. Routes can import service boundaries and Platform. Platform
can import only Platform within application source; `relkit.config.ts` can import Platform
fragments. Application code cannot depend on tests, migrations, scripts or other tooling.
Tooling can import the application for testing and operational work.

The compiler follows helper modules, re-exports, type-only edges and literal dynamic imports
using the project's effective TypeScript aliases. A barrel cannot make a private cross-service
import public. Computed dynamic imports and unresolved dynamic targets produce analysis-limit
warnings; they are not proof that the target respects a boundary.

Keep prompt text, JSON assets, schemas and local helper modules beside their consumer.
Assets move with their service but do not become independently discovered descriptors.

## Functions own behavior; dependencies grant clients

A function is where validated business input becomes a result. Keep HTTP parsing in routes and model
instructions in agents. The function declares the provider-backed resources it uses; putting a cache or bucket
in the same folder does not grant access automatically.

## Tools and agents stay with their business domain

Put an order lookup tool in Orders, not in a separate application-wide AI domain just because a model
calls it. A tool points at a function with `defineTool({ target: ... })` or adapts that function with
`.asTool()`. The schemas and business behavior stay with the function. Start with
[defining a tool](/docs/ai/tools) or [turning a function into a tool](/docs/ai/function-tools).

An agent's `agents/` file owns its instructions, schemas, model, tool allowlist, and execution limits.
Store long instructions in a local prompt module if that makes them easier to maintain. Plain text does
not need a new service. See [defining an agent](/docs/ai/agents).

To let a browser run an agent, expose its `client` contract and select it with the generated
`useAgent` hook. Every run, observation, control, and continuation supplies the application's stable
business thread ID. Agents and tools remain compiler-discovered domain files; do not add an `agents` or
`tools` map to `defineService`. A tool in another domain can target a public function from the owning
service; it should not import that domain's private tool file.

“Internal to the domain” does not mean “hidden from MCP.” Tools are exposed through MCP by default unless
disabled. Review [MCP access](/docs/ai/mcp) and [tool approvals](/docs/ai/approvals) before exposing them.

## Events and jobs belong to the work's owner

Put the fact in the producing domain's `events/` directory and the reaction in the receiving domain's
`functions/` directory. For example, Orders defines `orders.created`, while Receipts defines the
`defineEventFunction` that reacts to it. The subscriber stays out of `service.functions`: it runs through
event delivery or replay, not direct invocation.

A task and job belong to the domain responsible for completing the durable work. The task stays in that
domain's `tasks/` directory and the job owns its public name, admission, and schedules. A schedule is an
option on the job, not a separate service or a reason to move the task. Follow [your first event](/docs/events/first-event),
[jobs](/docs/jobs), and [schedules](/docs/jobs/schedules) for the complete workflows.

## Resources do not go in the service member list

Caches and buckets live under their owning domains. Functions declare `dependencies.cache` or
`dependencies.buckets`, and `relkit.config.ts` supplies provider bindings for the selected profiles.
Changing the provider does not require moving the domain's business code.

If another domain needs access, expose an operation on the owner—such as uploading or reading a file—
instead of publishing the raw cache or bucket as a service member. See the
[storage tutorial](/docs/storage/first-upload) for a bucket, function, service, and route working together.

Database and authentication integrations have specialized boundaries: `src/services/database/service.ts` uses
`defineDrizzleService`, with table schemas beneath that domain; `src/services/auth/service.ts` uses
`defineBetterAuthService`. They are not `database` or `auth` options on `defineService`. Start with
[Database](/docs/database) for setup, schemas, queries, and model customization. The compiler supplies
`context.database`; functions do not add a `dependencies.database` entry. Ordinary business domains
still expose operations through `defineService`. See the
[Database](/docs/database) and [Auth](/docs/auth) guidance when replacing older adapters, or
[Integrate Better Auth](/docs/database/better-auth)
to share the current database with authentication. Continue with [Auth](/docs/auth) for service setup,
sessions, route protection, clients, and authentication customization.

## Shared code is not a shortcut around ownership

Keep domain-specific schemas, constants, errors, and helpers with their owner. Other domains consume
public service operations instead of importing those private modules. A public function's declared
errors are part of its checked contract; you do not add an `errors` member map to the service.

Use `src/platform/` for genuinely shared, domain-independent support, such as the environment contract
or common schema primitives. Platform cannot import domains or routes. If a “shared” helper knows how
Orders calculates a total, it belongs to Orders.

Tests live outside `src/` in the generated layout. Unit tests can import the specific function they
exercise; integration tests verify the application's routes and runtime behavior. Do not add a domain
service just to hold tests.

## Let the compiler check the organization

Run these commands from your generated application's root after adding or moving artifacts:

```sh
bun run check
bun run typecheck
```

Expect a successful graph check and type check. Fix missing services, invalid IDs, unresolved targets,
and boundary errors before continuing. Do not register every file manually in `relkit.config.ts` or edit
`.relkit/generated`; the compiler derives the model from source.

Naming and folder-placement suggestions remain nonfatal convention warnings. They are
distinct from ownership, missing-boundary, mixed-layout and forbidden-import errors.
