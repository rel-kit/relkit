## Pull the public contract

Start with a running RELKIT backend and a separate React app that has `@relkit/client` and the
RELKIT CLI installed. From the frontend root, pull the server's public contract into a
frontend-owned directory:

```sh title="Terminal — frontend root"
bun run relkit client pull http://127.0.0.1:3000 --out ./relkit-client
```

This writes `contract.ts`, `client.ts`, `client-registry.d.ts`, and a manifest. Include the
generated declarations in your TypeScript project and regenerate them when the public API
changes. The backend must be reachable while you pull; do not import backend source into a
browser bundle.

## Enforce compatibility

The provider defaults to the same-origin backend, credentialed requests, a 30-second finite request
timeout, and a 10-second stream-establishment timeout. An established healthy stream is not capped by
the finite timeout. From the frontend root, check the pulled contract against the running
backend before shipping:

```sh title="Terminal — frontend root"
bun run relkit client check http://127.0.0.1:3000 --out ./relkit-client
```

For Next.js or Vite, `withRelkit()` or `relkit()` can inject the public fingerprint at build
time; the `client pull` command above is what writes the declarations.

The exact public-contract fingerprint must match. A mismatch enters `application-updated` and blocks
new typed work until frontend and backend are coordinated; unresolved mutation or control metadata is
preserved rather than retried.

Job hooks use the same provider and identity handshake. `useJobTrigger` retains the accepted `runId`, while
`useJobRun` observes that run without starting a subscription during server rendering. Unknown submission
outcomes remain visible for same-key recovery instead of becoming an automatic replay queue.
