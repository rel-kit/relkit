---
title: Run and add your first route
description: Start the generated API, understand the existing hello operation, then add and verify a new status endpoint.
---

You will first prove that the generated application works unchanged. Then you will reuse its Hello
function through a new route so the compiler, reload loop, OpenAPI document, and inspector all receive
a real source change. To add a new domain function and validated POST endpoint together, follow
[Your first HTTP route](/docs/http/first-route).

Start in the `relkit-orders` directory from [Create an application](/docs/start/create-an-app), with
dependencies installed and `.env` copied from `.env.example`. The commands below run inside that app,
not the RELKIT monorepo root.

## Run the generated route

<Steps>
  <Step>
    ### Start development

    ```sh title="Terminal — relkit-orders"
    bun run dev
    ```

    Keep this terminal open. RELKIT starts the backend on `http://localhost:3000` and the inspector on
    `http://localhost:3210`.

  </Step>
  <Step>
    ### Call the hello route

    In a second terminal:

    ```sh title="Terminal — relkit-orders"
    curl "http://localhost:3000/hello?name=RELKIT"
    ```

    Expected response:

    ```json title="HTTP 200"
    { "message": "Hello, RELKIT!" }
    ```

  </Step>
</Steps>

## Follow the domain operation

The Hello function owns validation and behavior:

<include cwd lang="ts" meta='title="src/hello/functions/hello.function.ts"'>
  ../../templates/default/v1/api/src/hello/functions/hello.function.ts
</include>

The owning service exposes it as `hello`:

<include cwd lang="ts" meta='title="src/hello/service.ts"'>
  ../../templates/default/v1/api/src/hello/service.ts
</include>

The route imports that service and targets `hello.hello`. Its folder supplies `/hello`, its named `GET`
export supplies the HTTP method, and the input schema supplies the `name` query parameter and its
`world` default. The request reaches the same function through this boundary:

```text
GET /hello?name=RELKIT → route → Hello service's hello operation → function → validated response
```

Keep business logic in the owning domain, not the route file. See [Service organization](/docs/service/organization)
for where to add functions and other capabilities, and [HTTP Routes](/docs/http) for transport details.

## Add a second route

<Files>
  <Folder name="src" defaultOpen>
    <Folder name="routes" defaultOpen>
      <Folder name="status" defaultOpen>
        <File name="route.ts" />
      </Folder>
    </Folder>
  </Folder>
</Files>

<Steps>
  <Step>
    ### Create the route directory

    Reuse the checked hello function through a second transport descriptor:

    This tutorial assumes `src/routes/status/route.ts` does not already exist. If your app already has
    that route, choose another unused path rather than overwriting it.

    ```sh title="Terminal — relkit-orders"
    mkdir -p src/routes/status
    cp src/routes/hello/route.ts src/routes/status/route.ts
    ```

  </Step>
  <Step>
    ### Understand the executable source

    The copied file is the canonical API-template route below:

    <include cwd lang="ts" meta='title="src/routes/status/route.ts"'>
      ../../templates/default/v1/api/src/routes/hello/route.ts
    </include>

    The filesystem folder changes the route path to `/status`; the `GET` export and hello target remain
    unchanged. `@app/*` maps to the project's `src/*` directory, so imports stay stable when a file moves
    deeper in the route tree. Keep the `.js` extension because the compiled application runs as ESM.

  </Step>
  <Step>
    ### Verify reload and transport output

    ```sh title="Terminal — relkit-orders"
    curl -i "http://localhost:3000/status?name=RELKIT"
    bun run check
    ```

    Expect `HTTP/1.1 200`, `{ "message": "Hello, RELKIT!" }`, and a successful check. OpenAPI, the
    generated client contract, graph, and inspector now contain both `/hello` and `/status`.

  </Step>
</Steps>

<Callout type="warn" title="Do not edit generated route data">
  Route identity, OpenAPI, the client, and graph files are derived from source. Correct the
  descriptor and rerun `check`; never patch `.relkit/generated`.
</Callout>

You now have two HTTP paths to one domain operation, without duplicating its handler or schemas.
Continue with [Local development](/docs/start/local-development) to inspect reloads and verify changes.
When you need a new business operation rather than another path, follow
[Your first service](/docs/service/first-service) and [Your first HTTP route](/docs/http/first-route).
