title: Build a production artifact
description: Produce the immutable server bundle, inspect its contents, and reject stale or invalid builds before release.
---

`relkit build` turns the checked application graph into a runnable production directory. Use it after tests
and typechecking, and before creating a container or deploying. The build is tied to the graph hash, so the
runtime can reject source and artifact combinations that no longer agree.

## Before building

Run the proofs that answer different failure classes:

```sh title="Terminal — relkit-orders"
bun run test
bun run check
bun run typecheck
```

Tests prove behavior, `check` proves RELKIT graph and policy validity, and TypeScript proves project-wide
static types. None replaces the other. Fix failures before building rather than treating the build as a
diagnostic loop.

## Create and inspect the artifact

<Steps>
  <Step>
    ### Build from the application root

    ```sh title="Terminal — relkit-orders"
    bun run build
    ```

    Expect exit code `0` and a reported graph hash. Building does not deploy, contact AWS, or start a
    long-running process.

  </Step>
  <Step>
    ### Inspect the output boundary

    <Files>
      <Folder name=".relkit" defaultOpen>
        <Folder name="build" defaultOpen>
          <File name="application.graph.json" />
          <File name="manifest.json" />
          <File name="openapi.json" />
          <Folder name="server" defaultOpen>
            <File name="index.js" />
            <File name="runtime.manifest.ts" />
          </Folder>
          <File name="Dockerfile" />
          <File name=".dockerignore" />
          <Folder name="public" />
        </Folder>
      </Folder>
    </Files>

    `server/index.js` is the runnable entrypoint. The graph and manifest describe exactly what was built;
    OpenAPI is the matching external contract. Container files package this same directory.

  </Step>
  <Step>
    ### Compare graph identity

    ```sh title="Terminal — relkit-orders"
    bun run relkit graph diff \
      .relkit/generated/application.graph.json \
      .relkit/build/application.graph.json
    ```

    Immediately after a build, expect no semantic difference. If source changed after the build, rerun
    `check`, the affected tests, and `build` instead of copying individual generated files.

  </Step>
</Steps>

## What belongs in a release

Treat `.relkit/build` as one immutable unit. Do not combine the server from one run with the manifest or
graph from another. A release system may archive the directory, build the generated Dockerfile, or pass the
directory to RELKIT deployment, but it should not rewrite generated files.

Environment values and secrets are deliberately absent. The artifact contains environment declarations and
provider references; actual values are resolved when the process starts in the target environment. This lets
the same artifact move through staging and production without embedding credentials.

## Common build failures

<Accordions>
  <Accordion title="The build says generated output is stale">
    Run `bun run check` and inspect the first diagnostic. Commit the corresponding source change and
    freshly generated contracts together, then rebuild.
  </Accordion>
  <Accordion title="A production-only policy is rejected">
    Development may use process-local providers. Production requires restart-safe or shared
    implementations for features such as distributed rate limiting. Configure the production
    provider instead of suppressing the diagnostic.
  </Accordion>
  <Accordion title="The artifact contains an unexpected route or resource">
    Use `bun run relkit graph print` to locate its source. Delete or exclude the authored
    descriptor, run `check`, and build again. Never delete only the generated node.
  </Accordion>
</Accordions>
