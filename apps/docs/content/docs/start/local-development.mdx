## Know the local surfaces

| Surface | Default address | What it shows |
| --- | --- | --- |
| Backend | `http://localhost:3000` | Your Orders routes |
| Inspector | `http://localhost:3210` | Functions, routes, requests, logs, and diagnostics |
| HTTP reference | `http://localhost:3000/_relkit/v1/api-reference` | Generated endpoint contracts |
| Readiness | `http://localhost:3000/_relkit/v1/health/ready` | Whether the active generation can serve |

Start `bun run dev` and open the Inspector. Choose **Routes**, then `POST /orders` to see the
public function it targets. Open **Functions** and find the Orders pricing and creation
operations. The inspector shows the checked application, not a second configuration to edit.

## See a failed reload safely

In `src/routes/orders/route.ts`, temporarily misspell `defineServiceRoutes` and save. The
development terminal reports a source diagnostic. The last valid generation remains active;
a new broken candidate does not replace it. Restore the spelling and save again.

Check readiness and the protected route after the repaired generation activates:

```sh title="Second terminal — relkit-orders"
curl -i http://localhost:3000/_relkit/v1/health/ready
curl -i http://localhost:3000/orders/private-1
```

Expect readiness success and `401` for the signed-out Orders request. If the app did not
reactivate, run `bun run check` and fix its first diagnostic. The last valid generation can
serve requests while a changed candidate is invalid, but an initial startup failure has no
previous generation to keep serving.

## Inspect the generated contract

Open the HTTP reference above and find `POST /orders` and `GET /orders/{orderId}`. Compare
their methods, paths, and request shapes with the source. The checked graph and OpenAPI files
under `.relkit/generated` are useful for diagnosis; repair source, then rerun `check`.

`bun run check`, `bun run typecheck`, and `bun run test` cover different concerns: graph
relationships, TypeScript types, and behavior.
