`bun run dev` runs the complete local feedback loop. It watches application source, checks a candidate
generation, starts it, verifies readiness, and only then makes it active.

This guide continues in the app created by [Create an application](/docs/start/create-an-app). The reload
exercise uses `/status` from [Run and add your first route](/docs/start/first-route); add that route first,
or use the existing `/hello` route and its source file instead. Keep `.env` loaded with the local defaults.

## Development endpoints

| Surface          | Default URL                                      | Use it for                                     |
| ---------------- | ------------------------------------------------ | ---------------------------------------------- |
| Application      | `http://localhost:3000`                          | Calling authored routes                        |
| Inspector        | `http://localhost:3210`                          | Graph, diagnostics, logs, requests, and traces |
| OpenAPI JSON     | `http://localhost:3000/_relkit/v1/openapi.json`  | Tooling and client generation                  |
| Scalar reference | `http://localhost:3000/_relkit/v1/api-reference` | Interactive HTTP documentation                 |
| Readiness        | `http://localhost:3000/_relkit/v1/health/ready`  | Confirming the active generation can serve     |

## Follow a source change

<Steps>
  <Step>
    ### Keep the supervisor running

    ```sh title="Terminal — relkit-orders"
    bun run dev
    ```

    Wait for both URLs before editing.

  </Step>
  <Step>
    ### Make an invalid edit safely

    Temporarily misspell `defineRoute` in `src/routes/status/route.ts` and save. The candidate fails with a
    source-located diagnostic, while the last valid `/status` generation remains active.

  </Step>
  <Step>
    ### Repair and verify activation

    Restore `defineRoute`, save, and call:

    ```sh title="Terminal — relkit-orders"
    curl "http://localhost:3000/status"
    curl "http://localhost:3000/_relkit/v1/health/ready"
    ```

    The status route returns `{ "message": "Hello, world!" }`; readiness succeeds for the new generation.

  </Step>
</Steps>

## Configure ports and body limits

The API template's configuration shows the server port, maximum request body size, and inspector port:

<include cwd lang="ts" meta='title="API template — relkit.config.ts"'>
  ../../templates/default/v1/api/relkit.config.ts
</include>

Cloud and deployment default to `none`; the generated configuration therefore contains no AWS or Pulumi
selection. Passing `--cloud aws --deploy pulumi` adds those explicit imports and roles, but still provisions
nothing until a deployment command runs.

Application port precedence is `--port`, `PORT`, `server.port`, then `3000`. Inspector precedence is
`--inspector-port`, `RELKIT_INSPECTOR_PORT`, `inspector.port`, then `3210`.

To choose different ports for one local run, stop the current development process and run:

```sh title="Terminal — relkit-orders"
bun run dev --port 3002 --inspector-port 3212
```

Use the printed URLs for subsequent requests. For request-size behavior, see [HTTP requests](/docs/http/requests).

<Accordions type="multiple">
  <Accordion title="The backend port is already in use">
    Run `bun run relkit doctor --no-pulumi --port 3000 --inspector-port 3210`. Stop the reported
    process or choose a different port.
  </Accordion>
  <Accordion title="A save does not activate">
    Read the first candidate diagnostic and run `bun run check`. A schema, graph,
    provider-readiness, or evaluation error prevents activation by design.
  </Accordion>
  <Accordion title="Stopping development">
    Press `Ctrl-C` once in the supervisor terminal. RELKIT forwards shutdown to both child
    processes.
  </Accordion>
</Accordions>

Installed projects use the inspector bundled with `@relkit/cli`. `RELKIT_INSPECTOR_ROOT` is only for
framework contributors selecting another compatible inspector checkout.

## Control declared local services

`check` writes a deterministic local-service plan without probing Docker. During `dev`, RELKIT starts only
the graph-required `docker(adapter)` recipes and waits for their protocol health checks before activation.
Unchanged healthy services and persistent volumes survive candidate reloads.

```sh title="Terminal — relkit-orders"
bun run relkit local status
bun run relkit local up --detach
bun run dev --local=off
bun run relkit local stop
```

Use `--local=off` when you want every required binding to resolve from its connected or infrastructure
values. `local reset --yes` also removes this project's labelled volumes and override state; it refuses a
live attached lease and never targets another checkout.

## Verify changes

From the application root, run these checks after changing a function, service, route, or configuration:

```sh title="Terminal — relkit-orders"
bun run check
bun run typecheck
bun run test
```

`check` validates RELKIT's application graph and refreshes generated contracts; `typecheck` checks
project-wide TypeScript types; tests exercise behavior. Fix the first source-located diagnostic and
rerun the checks. A valid graph alone does not prove business correctness or provision external services.

Inspect `.relkit/generated/application.graph.json` and `diagnostics.json` when troubleshooting, but
change the authored source rather than generated files. For command flags, see
[`relkit check`](/docs/operations/cli-reference#relkit-check). For focused tests and fakes, see
[Testing](/docs/operations/testing); for runtime investigation, see [Inspector](/docs/operations/inspector)
and [Troubleshooting](/docs/operations/troubleshooting).

When you need to check a release locally, stop `dev`, run `bun run build`, then `bun run start`. Building
and starting are not cloud deployment. Use the CLI reference for
[`build`](/docs/operations/cli-reference#relkit-build) and [`start`](/docs/operations/cli-reference#relkit-start),
and [Deployment](/docs/operations/deployment) only when you are ready to configure cloud resources.
