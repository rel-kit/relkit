title: Generated clients

---

The generated client is a consumer of the checked HTTP contract. It derives operation names, input types,
output types, and declared transport errors from routes and schemas. Do not hand-write a second interface for
the same API; it will drift when request mapping or response contracts change.

## Generate and instantiate the client

<Steps>
  <Step>
    ### Refresh the contract

    ```sh title="Terminal — relkit-orders"
    bun run check
    ```

    This writes `.relkit/generated/contract.ts` and `.relkit/generated/client.ts`. Both are generated and must
    be committed or packaged according to the repository's release policy, never edited directly.

  </Step>
  <Step>
    ### Configure one transport instance

    <include cwd lang="ts" meta='title="examples/commerce/src/generated-client.ts"'>
      ../../examples/commerce/src/generated-client.ts
    </include>

    Set `baseUrl` to the deployed API origin. Add authentication through a controlled header provider or
    request boundary rather than embedding a token in generated source.

  </Step>
  <Step>
    ### Call a generated procedure

    Use editor completion on the generated contract to select the route operation and supply its inferred
    input. The client maps path, query, header, cookie, and body fields according to the route descriptor.

  </Step>
  <Step>
    ### Test against the in-process application

    Point the client transport at a test server or use `createTestApplication` for route-level integration.
    Assert one success, one validation failure, and one declared application error.

  </Step>
</Steps>

## Handle errors by contract

Transport failures use `ORPCError`; declared application errors retain stable codes and validated data. Match
the stable code and status your application contract promises. Do not branch on a formatted message that may
change for clarity or localization.

A middleware-only native response is not automatically included in the generated error union. If consumers
must handle it, add it to the route contract and test that the runtime and generated types agree.

## Route-shape edge cases

Catch-all values are arrays of path segments. The client URL-encodes each segment independently, so a value
containing `/` cannot escape its position and alter route structure. Optional catch-all routes may register
both the base and expanded runtime paths while remaining one client operation.

## Keep consumers current

Run `check` whenever a route or schema changes, review the generated contract diff, and publish the client
artifact with a compatible version. A newly required field, removed operation, changed stable error code, or
narrowed output is a consumer migration even if the server still compiles.

<Callout title="Generated does not mean unreviewed">
  Review generated contract changes as carefully as authored API changes. Automation prevents drift;
  it does not decide whether a breaking change is acceptable.
</Callout>
