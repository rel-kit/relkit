RELKIT generates a typed client from checked function-backed routes. Operation names come from route
IDs; input, output, and declared application errors come from the target functions.
Raw handlers do not become generated-client operations.

The client uses **RPC over `/rpc`**, not HTTP request mapping to the original REST URL. Use the
[OpenAPI document](/docs/http/openapi) or an ordinary HTTP caller when you need that exact REST contract.

## Generate the contract

From your application's root:

```sh
bun run check
```

This writes `.relkit/generated/contract.ts` and `.relkit/generated/client.ts`, alongside graph,
OpenAPI, and JSON client-contract artifacts. Never hand-edit them.

Make the generated contract part of the caller's TypeScript program: import the generated client
entry point, or explicitly include the generated contract when using `@relkit/client` directly.
The contract augments the default client registry so operation names and inputs are typed. Merely
installing `@relkit/client` in another app does not teach it your server's operations.

Package or share the generated client and contract together with the dependencies they import.
Regenerate and review them when route identities, input, output, or errors change.

Set `baseUrl` to the backend origin, without appending `/rpc`; the client adds that transport path.
The snippet uses port `3000`, the generated-app default. Change it to `4000` when calling the commerce
app with its default configuration.

`headers` accepts a header collection or a provider, including an asynchronous provider.
Use request-scoped headers or a provider for credentials; do not mutate one shared instance with
different users' credentials in a server process. The example's mutable `liveHeaders` is not a
multi-user session store. Browser credentials default to `include`; cross-origin cookies still
require appropriate browser, cookie, and server CORS configuration. A custom `fetch` is supported.

## Call with domain input

Select the checked route ID with editor completion. For the unmodified Echo tutorial, the operation
is `route.post.echo` and the input is `{ message: "hello" }`. It resolves to the function's validated
output, not a native `Response`.

| Original REST route                                     | Generated RPC call                                        |
| ------------------------------------------------------- | --------------------------------------------------------- |
| Maps path, query, headers, cookies, and body into input | Accepts the target function's input directly              |
| Uses the route's `request` mappings and transforms      | Does not replay those mappings or transforms              |
| Returns the selected HTTP success status and body       | Resolves to typed function output                         |
| Returns an HTTP error envelope                          | Rejects with an RPC error                                 |
| Handles multipart according to the route                | Does not automatically reconstruct that multipart request |

For example, the Orders REST route obtains `orderId` from `idempotency-key`; an RPC caller supplies
the function's `orderId` input property. Sending that header alone does not fill the RPC input.
Likewise, catch-all input is an array supplied to the function, not a REST path the client constructs.

## Handle failures by contract

RPC failures use `ORPCError`. Declared application errors retain their stable error code and data;
unexpected failures use transport-level codes. Branch on the code and validated data, not a formatted
message. Do not expect a REST validation `422` body to be the RPC error shape.

A response returned by HTTP middleware is not automatically a declared function error. The RPC
middleware bridge maps a returned `401` to `UNAUTHORIZED`, a `429` to `TOO_MANY_REQUESTS`, and other
returned responses to `INTERNAL_SERVER_ERROR`. Test these cases if middleware protects the operation.

## Test security at both entry points

Registered Better Auth protection checks the operation's original route path for RPC session
requirements. Associated path-scoped middleware is also replayed, while global middleware surrounds
the RPC request. The middleware sees the native `/rpc` request, not synthetic REST parameters or body.

The route's `rateLimit` wrapper is **not applied to RPC calls**. A REST-only limit or middleware that
assumes the original URL is therefore insufficient to protect every caller. Apply equivalent policy
at the RPC boundary or in shared domain authorization, and test both reachable transports.

Point the client at a running local test server. The current `createTestApplication` HTTP helper does
not serve `/rpc`, so connecting it through a custom `fetch` is not an RPC integration test.
Cover success, invalid input, a declared error, missing credentials, and any quota policy.
Keep REST tests too; RPC tests do not exercise request mapping. See [Testing](/docs/operations/testing)
for the other available test layers.

## Review compatibility changes

Changing an inferred route ID renames the client operation. A required input field, a removed error
code, or a narrowed output can break consumers even if the server compiles. Compare generated
artifacts in review and version shared contracts with their callers.
