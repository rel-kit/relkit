Deployment is optional and begins only after the application passes its local checks and build. Pulumi is the
deployment engine and AWS is the first host integration, but engine, host, application resources, access, and
runtime wiring remain separate roles.

<Callout type="error" title="Authorization and cost required">
  These commands can create billable resources. Use an isolated account and stack, confirm the
  target, review every preview, and continue only when authorized to incur cost.
</Callout>

## Run a built application

Run `bun run build` in the development installation first. The build publishes the executable
`.relkit/build/server/index.js`, its graph and manifests, public assets, and any selected immutable
job workers. Copy the complete `.relkit/build` directory into the same relative path in your
production application root.

The build's `package.json` declares exact observed versions of selected runtime integrations and
their required SDKs. Required dependency patches and overrides travel with this manifest; keep the
complete output, including `patches/` when present. Install it before starting from the application root:

```sh title="Terminal — production application root"
cd .relkit/build
bun install --production --network-concurrency 1
cd ../..
NODE_ENV=production bun run --no-env-file .relkit/build/server/index.js
```

The framework runtime is bundled. This production installation does not need the development CLI,
compiler, Inspector application, or unselected SDKs. `relkit start` remains a convenience command
where the CLI is installed; the generated `start` script uses the JavaScript command above.

Supply required application environment values through the process environment. Startup does not
automatically read dotenv files, and build output does not inline their values. `PORT` overrides the
configured listener port. Run from the application root so default local provider state remains at
`.relkit/state`; public assets are resolved beside the built server. Keep existing state and
immutable job generations when replacing build output.

The generated Dockerfile uses `.relkit/build` as its build context. It installs the selected production
manifest and copies the complete server, public assets, graph, and selected worker history. Environment
files, existing local state, and temporary build module links are excluded from that context.

## Preview before applying

From the generated project:

```sh title="Terminal — relkit-orders"
bun run check
bun run test
bun run build
bun run relkit doctor --pulumi
bun run relkit deploy init --stack development
bun run relkit deploy preview --stack development
```

Use a separate stack for each isolated environment. Supported backends are Pulumi Cloud, local state, and object
storage URLs. Use repeatable `--config key=value` options for non-secret values and `--config-secret key=value`
for Pulumi secrets.

Preview generates and validates the Pulumi program from the graph. Review create, update, replace, and delete
operations before applying:

```sh title="Terminal — relkit-orders"
bun run relkit deploy up --stack development
bun run relkit deploy outputs --stack development
```

`--non-interactive` (alias `--yes`) approves protected operations for automation; it does not replace review or
authorization.

## Understand resource ownership

An infrastructure wrapper such as `aws(s3(...))` or `aws(redis(...))` may contribute supported lifecycle and
least-privilege access operations. A configured adapter passed directly to `defineApp` contributes runtime wiring
but no resource lifecycle. `docker(adapter)` is development-only and never becomes cloud infrastructure.

Job deployment publishes the immutable task worker and registers schedules only after readiness. Keep the
previous worker generation and its routing keys while it owns accepted runs; deployment does not rewrite run
history or turn a provider without native support into a durable fallback.

The AWS host owns ECS/Fargate hosting, networking, the workload role, load balancing, and CloudWatch routing for
redacted structured stdout. It does not implicitly own application jobs, events, model providers, Sentry, or
OTLP.

## Reconcile and clean up

For an isolated temporary stack:

```sh title="Terminal — relkit-orders"
bun run relkit deploy refresh --stack development
bun run relkit deploy destroy --stack development
```

Confirm the stack before destruction and verify cleanup independently. Never edit the generated Pulumi program
to bypass graph or role validation; repair configuration or integration support, run `check`, and preview again.
