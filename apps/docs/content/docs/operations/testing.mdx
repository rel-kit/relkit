Use the smallest layer that proves the behavior. Function tests exercise one descriptor without a server.
Application tests load checked configuration and call an in-process HTTP client. Neither layer needs remote
credentials when provider-backed capabilities receive explicit fakes.

## Test one function

Use `invokeFunction` for input and output validation, declared errors, nested invocation, and handler behavior:

<include cwd lang="ts" meta='title="templates/default/v1/api/tests/unit/orders.function.test.ts"'>
  ../../templates/default/v1/api/tests/unit/orders.function.test.ts
</include>

```sh title="Terminal — relkit-orders"
bun test tests/unit/orders.function.test.ts
```

Pass test clients when the function declares cache, bucket, job, event, or model capabilities. Keep these fakes
deterministic and inspect their recorded effects instead of sleeping or calling a live service.

## Replace provider profiles explicitly

The commerce suite shows the complete shape for multiple cache, bucket, and model profiles:

<include cwd lang="ts" meta='title="examples/commerce/tests/http.test.ts"'>
  ../../examples/commerce/tests/http.test.ts
</include>

Every graph-required capability and profile must have a replacement. `RELKIT_ENV=test` does not silently select
fakes. Use `createTestCacheFake` and `createTestBucketFake` for deterministic resource behavior, and dedicated
test event, job, or agent utilities for those contracts.

## Run the application gate

```sh title="Terminal — relkit-orders"
bun run test
bun run check
bun run typecheck
bun run build
```

Keep live integration and cloud tests separate and opt-in. In the RELKIT repository, `bun run prepush` runs all
locally reproducible required CI jobs and expects Docker to be available.
