# ZSYS-DR-002: Filesystem Structure, Resource Addressing, and One-Command Deployment

**Date:** 2026-08-06

**Status:** Proposed

**Owners:** ZSys maintainers

**Related records:** [ZSYS-DR-001](./2026-08-06-001-foundational-architecture.md)

**Related brief:** [`../briefs/2026-08-06-project-brief.md`](../briefs/2026-08-06-project-brief.md)

## Context

ZSys needs a project structure as predictable as Next.js routing conventions, but capable of describing a complete application: API routes, views, entities, modules, realtime channels, caches, agents, workflows, tools, databases, deployment providers, UI surfaces, documentation, and observability.

The structure must serve TypeScript developers and AI agents, produce deterministic addresses for application resources, and support a single deployment command without hiding infrastructure changes or trapping developers in generated code.

## Options discussed

### Option A: Global capability directories

```text
routes/
views/
entities/
workflows/
agents/
tools/
```

This is easy to discover in small projects, but one feature becomes distributed across many root directories. Changes to a domain such as billing or identity require navigation across unrelated locations, ownership becomes less obvious, and module extraction becomes harder.

### Option B: Domain modules as the physical boundary

```text
modules/
  identity/
    module.ts
    entities/
    api/
    views/
    realtime/
    workflows/
    agents/
    tools/
    jobs/
    emails/
    policies/
```

This keeps one business capability together. Global category views can still be generated by the CLI, graph explorer, documentation, and editor integrations.

### Option C: Give every resource an HTTP-style URL

This creates a familiar mental model, but databases, caches, internal tools, entities, and workflows should not be treated as publicly reachable network endpoints.

### Option D: Give every resource a canonical logical address

Every resource receives a stable scheme-based identifier, while public URLs are generated only for exposed surfaces.

Examples:

```text
route://identity/users/:userId
view://identity/users/:userId
entity://identity/user
workflow://identity/invite-member
agent://identity/onboarding
tool://identity/find-member
channel://identity/presence
database://main
cache://sessions
stack://production/api
```

## Decision or current direction

### D-011: Use domain modules as the source-tree ownership boundary

The physical repository should be organized primarily under `modules/<module-id>/`. Root-level `apps/`, `resources/`, `ui/`, and `deploy/` directories describe application surfaces and shared bindings. Category-oriented navigation should be virtual rather than forcing category-oriented source ownership.

### D-012: Use deterministic filesystem conventions

ZSys should reserve well-known files and path syntax, including:

```text
module.ts       module declaration and public exports
route.ts        API endpoint declaration
page.tsx        web view
layout.tsx      surface layout
[id]/           dynamic segment
[...path]/      catch-all segment
(group)/        organizational or policy group omitted from the public path
_private/       implementation that cannot be exported outside its module
```

The compiler must report collisions for HTTP method, host, and path combinations as well as event names, channels, workflows, tools, database names, table names, Redis namespaces, and cloud resource identities.

### D-013: Use canonical resource addresses as compiler identities

Logical addresses are stable graph identities and should be independent of a stage-specific domain, provider, or deployment location. Deployment manifests map logical addresses to concrete URLs and resource bindings.

### D-014: Derive route paths from the filesystem while keeping contracts explicit

The filesystem supplies the route path. oRPC declarations supply methods, input/output contracts, authorization, and handlers. The compiler may generate Hono registration, OpenAPI, Scalar references, typed clients, telemetry hooks, and graph edges from the same declaration.

A native Hono or oRPC implementation remains valid through an escape hatch that supplies sufficient metadata for graph discovery.

### D-015: Separate logical capabilities from provider bindings

Feature modules request capabilities such as database, cache, email, storage, queue, and telemetry. Stage declarations bind those capabilities to local or hosted implementations. Business modules should not import provider-specific credentials or infrastructure constructs directly.

### D-016: Make deployment one command but multiple auditable phases

The primary command should be:

```bash
z deploy --stage production
```

The command should expose a plan and execute explicit phases:

1. Discover declarations.
2. Build the normalized Application Graph.
3. Validate routes, schemas, policies, dependencies, and resource identities.
4. Generate contracts, clients, registries, documentation, diagrams, and infrastructure input.
5. Type-check and run contract tests.
6. Produce an infrastructure and migration plan.
7. Require approval for destructive or policy-restricted changes.
8. Apply infrastructure through the selected adapter.
9. Run safe database migrations.
10. Deploy services and static applications.
11. Run smoke and health checks.
12. Emit a machine-readable deployment manifest.

SST should be the first optimized deployment adapter. Direct Pulumi and selected Alchemy adapters can follow without changing the logical Application Graph.

### D-017: Provide deterministic human and agent inspection commands

At minimum:

```bash
z routes --json
z entities --json
z workflows --json
z urls --stage production --json
z inspect route://billing/invoices --json
z impact entity://billing/invoice --json
z graph --format json
z plan --stage production --json
z deploy --stage production --json
```

Readable canonical property names remain the source format. Optional short aliases may be accepted only in a versioned machine dialect and must normalize immediately to the canonical AST.

### D-018: Share application semantics across platforms, not necessarily one UI tree

Web, mobile, and desktop targets may share contracts, entities, policies, workflows, form schemas, navigation identities, design tokens, and view models. Next.js, Expo, and desktop adapters may render platform-specific UI rather than forcing identical components across all targets.

## Consequences

### Benefits

- Predictable discovery comparable to filesystem routing frameworks.
- Strong domain ownership and easier module extraction.
- Stable references for documentation, diagrams, diagnostics, deployment output, and AI-agent tools.
- Provider portability because feature code depends on capabilities rather than vendors.
- One deployment entry point without concealing plans, migrations, or infrastructure changes.
- Generated global views without sacrificing a domain-oriented repository.

### Costs and risks

- Convention growth can become difficult to learn unless diagnostics, editor tooling, and documentation remain excellent.
- Logical address versioning becomes a compatibility concern for links, policies, telemetry, and generated clients.
- Filesystem inference cannot safely determine every graph relationship; explicit declarations and overrides will be required.
- A single deployment command coordinates systems with different rollback properties, especially infrastructure, application code, and database migrations.
- Cross-platform generation can overpromise unless shared semantics and renderer-specific behavior are clearly separated.

## Open questions

1. Which special files and directory names belong in the initial stable convention set?
2. Are resource addresses globally unique within a workspace or namespaced by application?
3. How are route versions, custom domains, and multi-tenant hostnames represented without changing logical route identities?
4. Which deployment steps require interactive approval, policy-as-code approval, or CI-only approval?
5. What is the deployment manifest schema, and which parts are safe to commit?
6. How are aliases and renamed resources represented so telemetry, clients, and migrations remain traceable?
7. Should global virtual views be exposed through generated files, an editor extension, an MCP server, or all three?

## Follow-up actions

- Specify the first filesystem grammar and reserved names.
- Define canonical resource-address parsing and normalization rules.
- Add collision diagnostics with stable error codes.
- Define the deployment manifest and `z urls --json` schema.
- Prototype one domain module containing an entity, oRPC endpoint, Hono binding, Next.js view, Redis cache dependency, and SST deployment.
- Test the same Application Graph against local and preview stage bindings.
- Document provider escape hatches and module-level detachment behavior.
