# RelKit 0.9.2 release candidate

Deterministic release output generated from checked-in package and template metadata.

## Changes

### Fixed

- the API reference declares the error body the Better Auth endpoints send. Every 4xx and 5xx JSON response of an authentication operation refers to the new `BetterAuthError` schema (`message`, usually `code`, and `issues` on a validation failure) in place of the `message`-only schema Better Auth's generator writes. The errors themselves are unchanged: they stay in Better Auth's format and are not Problem Details. The 403 of a state-changing operation, such as `POST /api/auth/organization/set-active`, also lists `application/problem+json`, which RelKit's transport policy sends for a request from another origin. `POST /api/auth/get-session` is listed only when `session.deferSessionRefresh` is set, because Better Auth answers 405 to it otherwise.
- `profile` in `defineBucket`, `defineCache`, `defineEvent`, `defineEventFunction` and `defineChannel` accepts only the profile names your application configures for that capability, and `"default"` when the capability has a single adapter. Your editor suggests them, and a name that is not a profile is a type error instead of a failure of `relkit check`. The names come from the generated context registry; run `relkit check` once so it carries them. Without them, as in a library, `profile` accepts any string. For a name built in code, use `ProviderProfileName` from `relkit/contracts`. Fixed: an option that `defineFunction` or `defineEventFunction` does not have is a type error on that option, such as `Type 'number' is not assignable to type 'UnknownOption<"timeout">'`; before, it was accepted without an error and had no effect. A project that has such an option now fails to type-check until the option is removed. The removed option `publishes` is no longer suggested, and its error names what replaces it: `RemovedOption<"publishes", "dependencies.events">`. Fixed: your editor suggests both values of `execution` in `defineTask` on TypeScript 5.9; before, it suggested `durable` only. `defineTask` and `defineTaskEffect` type the option through a parameter that defaults to every form; a task that leaves `execution` out is durable, as before. The API reference prints `ServerConfig`, `InspectorConfig` and the telemetry options with their members, and the `defineApp` options block lists the seven provider options. `AppTelemetryConfig` is an interface that lists its members; it accepts and produces the same values as before. Every option of the authoring APIs (`defineFunction`, `defineError`, `defineRoute`, `defineServiceRoutes`, `defineEvent`, `defineEventFunction`, `defineChannel`, `defineBucket`, `defineCache`, `defineTask`, `defineJob`, `defineService` and the environment builders) shows a one-line description in your editor and on the API reference pages. Fixed: `defineRoute` is one signature for a function route and a raw route. A mistake in an option is reported on that option; before, TypeScript 5.9 reported "No overload matches this call" on `defineRoute` itself. `defineRoute` and `defineRouteEffect` take the type parameters `Id`, `Target`, `Request` and `Handler`; calls that pass no type arguments are unaffected.
- Changed: a run of a task that declares `maxElapsed` is accepted. Before, the submission failed with `Inngest cannot certify task policy field "maxElapsed".` Inngest does not enforce the limit; `relkit check` and the server's start now report that with `RELKIT_JOB_TASK_OPTION_UNSUPPORTED`. The error for a task option Inngest cannot map names the backend and the option: `The inngest jobs backend does not support the task option "<name>". Remove it from the task.`
- Added: `relkit check` warns with `RELKIT_DEPRECATED_TASK_LOGGING` for each task that sets the deprecated `logging` option, naming the task. The check still passes.
- The type of the service returned by `defineBetterAuthService` carries the role and permission names of the instance's organization plugin (`ac.statements` and the keys of `roles`, or the plugin's defaults). `InferBetterAuthAccess` reads them; the generated context registry uses it to type function access rules. Roles are `string` with `dynamicAccessControl`, and both are `string` without the organization plugin.
- `relkit dev` and `relkit check` write `interface ApplicationProfiles` into `.relkit/generated/context-registry.d.ts`, so `profile` in buckets, caches, events and channels is typed by the profile names of `relkit.config.ts`. Commit the changed file.
- in `defineApp`, your editor suggests the profile names for each entry of `defaults`, at an empty value and inside quotes, and `"default"` for a capability with a single adapter. A name that is not a profile is one type error on that entry that lists the valid names; before, every entry of `defaults` was reported. A default for a capability without a provider is one type error that names the capability (`NoProviderConfigured<"model">`), and an option `defineApp` does not have is a type error even when the call configures providers. Every option of `defineApp`, `server`, `inspector` and `telemetry` now shows a description in the editor. `defineApp` and `defineAppEffect` take one type parameter per provider capability instead of one for all of them. Calls that pass no type arguments, which is how applications call them, are unaffected. Fixed: with a Better Auth service that uses the organization plugin, `access.roles` and `access.permissions` of a function accept only the names of the plugin's access control. Your editor suggests them, and a misspelled name is a type error; before, it was accepted and every caller got a `403`. Run `relkit check` once so the generated context registry carries the names. For a name built in code, use `AccessRoleName` and `AccessPermissionName` from `relkit/contracts`. Fixed: `defineFunction` is one signature instead of two overloads. A mistake in its options is reported once, where it is, instead of as "No overload matches this call" followed by errors in the handler, and your editor suggests the kinds of `dependencies`.
- Every option of `createTestApplication` and `createTestRuntime` shows a one-line description in your editor and on the API reference page.
- `createTestApplication` honours its `context` option. The fields you pass reach handlers and replace the application's own, such as `auth` or `database`, as they do in `createTestRuntime`. Before, the option was accepted and ignored.
- an event function without `profile` uses the application's default event profile (`defaults.event`), or its only event profile, as an event without `profile` does. Before, the definition wrote the profile `default`, so an application with only named event profiles failed `relkit check` unless every event function repeated the profile. A client that publishes an event without a profile uses the only profile of its source. One case behaves differently after the upgrade: an application that has an event profile named `default` beside others and sets `defaults.event` to another one. An event function without `profile` used `default` there and now uses `defaults.event`. Add `profile: "default"` to keep the old binding. The `profile` of an event function's descriptor is optional in its type and absent when the definition names none. Fixed: the fields an event lists in `sensitiveFields` are recorded as `[REDACTED]` wherever RelKit records the event's payload: the span of the function that publishes it (input and output), the span of each event function that receives it, on delivery and on replay, and so the Inspector's trace views and telemetry exporters that send those records. Before, the option was stored and shown as a label and nothing was redacted. Publishers, event functions and replay receive the real payload. A name matches a key anywhere in the payload; a dotted path such as `customer.email` matches from its root. Fixed: the local jobs backend enforces `maxDuration` and `maxElapsed` of a task. Before, both were ignored. An attempt that works longer than `maxDuration` fails with `RELKIT_TIMEOUT` and is retried while the task's `retry` allows it; time asleep or waiting to retry does not count. A run that reaches `maxElapsed`, counted from its acceptance, is not retried. A run stopped by either limit ends with the status `timed-out`. After the upgrade, a task on the local backend that declares a limit and ran longer than it now times out. Added: the diagnostic `RELKIT_JOB_TASK_OPTION_UNSUPPORTED` for a task limit that the selected jobs backend does not enforce.
- `relkit dev` and `relkit check` write `interface ApplicationAccess` into `.relkit/generated/context-registry.d.ts` when the application has a Better Auth service, so function access rules are typed by the names of its access control. Commit the changed file.
- a run of a task that sets the deprecated `logging` option is accepted. Before, Inngest refused it.
- `relkit check` names a provider profile that a descriptor names and the application does not have (`Provider profile "x" does not provide event.`). Before, it reported the use as unqualified. Added: `relkit check` warns with `RELKIT_JOB_TASK_OPTION_UNSUPPORTED` for each `maxDuration` or `maxElapsed` of a task whose jobs backend does not enforce it, naming the task, the option, the backend and the profile. The server logs the same warnings when it starts. The check still passes. Changed: a check that passes prints its warnings above the `Checked` line. Before, the warnings of a passing check were only in `--json`. The exit code does not change.
- under `relkit dev`, the response of the client's live update stream (`GET /_relkit/v1/client/contract-events`) carries `x-request-id`, as every other answer of the development port does.
- fix: close the contract gaps and make the editor suggest names in the authoring APIs
- The local jobs backend declares that it enforces `maxDuration` and `maxElapsed` of a task (the adapter features `task-max-duration` and `task-max-elapsed`), so `relkit check` does not report those limits for tasks that run on it.
- Deprecated: the `logging` option of `defineTask`. It never had an effect: no jobs backend read its `level` or its `redact` list. The option is still accepted and shown in the graph, the editor marks it as deprecated, and it will be removed in a later version. It is no longer sent to a jobs backend with a run. Remove it from the task. Added: the diagnostic `RELKIT_DEPRECATED_TASK_LOGGING`.
- on Node, the 431 answer to a request with oversized headers carries `x-request-id`. Node's HTTP parser refuses such a request before a route is chosen; RelKit's Node adapter now writes that answer. On Bun the runtime writes it before any RelKit code runs, so it has no request ID there. The generated OpenAPI document has an `info.description` that says once what every route answers without a listed operation: a `GET` route also answers `HEAD`, `OPTIONS` answers `204` with `Allow`, and the HTTP server answers `431` before a route is chosen. With a mounted Better Auth service, the served document's Authentication section also says that those operations answer errors in Better Auth's format and not as Problem Details.
