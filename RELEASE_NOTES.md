# RelKit 0.9.1 release candidate

Deterministic release output generated from checked-in package and template metadata.

## Changes

### Breaking

- RelKit now requires and installs Better Auth 1.7.7 instead of 1.7.1, so `npm audit` no longer reports the critical `better-auth` advisory (OAuth Proxy and OAuth state sign-in as another user, GHSA-r4xp-prcw-77qf and GHSA-965c-763c-88jm) or the low `@better-auth/drizzle-adapter` one (rate limits on PostgreSQL, GHSA-44jh-23m7-hpcf). Better Auth 1.7.3 and later never write the required `account.issuer` column that projects created for 1.7.1 declare, and refuse to start while the Drizzle schema declares it. `relkit add auth` now generates the account table without `issuer` and without the unique index on `issuer` and `accountId`, for SQLite, PostgreSQL and MySQL. An existing project runs `relkit migrate --write`, which removes the column and its index from the schema file, then `db:generate` and `db:migrate`; no user, account or session is lost. See [Remove the account issuer column](/guides/migrate/relkit-0-9#better-auth-account-issuer). When the project's schema does not match the installed Better Auth release, auth now stops at startup with `RELKIT_AUTH_SCHEMA_MISMATCH`, naming each table and column and the change to make, instead of logging Better Auth's "Drizzle schema mismatch" and failing every sign-up and sign-in.

### Fixed

- The Inspector API's publication rows carry `producerTraceId` and `originRequestId`, so an event's publication links to its trace and to the request that caused it. Payloads stay out of the list, as before. When the application refuses an Inspector request with its own Problem Details answer, the Inspector keeps that answer and names the reason (for example the origin check) in place of a bare HTTP status.
- A 500 or 502 response no longer carries the cause of a provider or unexpected failure in any mode, development included (D10); its `detail` is the generic message. The cause is recorded instead: in development, one error log record with the redacted cause (`exception.type`, `exception.message`, `exception.stacktrace`, correlated by request, trace and span ID) and an `exception` event with the same attributes on the request span; in other modes, the failure's class only (`exception.type`, `relkit.error.code`), without message text. Bound parameters a database driver appends to a failed query (`params: …`) are masked. The invocation span gets an `exception` event naming the failure's class in every mode. A declared application failure records its identifier as `relkit.error.id` on the invocation span and on the request span. The `http.validation.failed` event carries `relkit.validation.issue_count` and, for the first ten issues, `relkit.validation.issues.<n>.code` and `relkit.validation.issues.<n>.path`, never messages or values; it is now also recorded when the function's own input validation rejects a request. An HTTP route whose function has an access rule with `roles` or `permissions` now answers 401 (no session) or 403 (missing role or permission) before it reads or validates the request input, so the answer names no input field. Rules with an `allow` predicate, which reads input, still run after validation. JSON bodies are decoded strictly: strings are converted to numbers and booleans only for values read from the path, query, headers and cookies. A JSON body value of `"3500"` for an integer field is now a validation error instead of being accepted as `3500`. A route that maps JSON body fields rejects a body that is not a JSON object (`null`, an array, a string or a number) with one validation issue, code `body-not-object`. Before, such a body counted as "no fields": a `PATCH` succeeded as an empty change and a `POST` reported each field missing. JSON and Problem Details responses of function routes now carry an explicit `Content-Length` (so `HEAD` reports the length of the `GET` body instead of 0), `X-Content-Type-Options: nosniff`, and `Cache-Control: no-store` unless the route's `response` option sets its own `Cache-Control`. With transport security configured, an `OPTIONS` request is treated as a CORS preflight only when it carries `Access-Control-Request-Method`. Any other `OPTIONS`, including one with a same-origin `Origin`, is no longer answered 403 `origin-denied`; it gets the application's normal answer with the allowed methods in `Allow`. Problem Details bodies now carry `requestId` next to `traceId`; it equals the response's `x-request-id` header, so a client can quote the same ID the server logs. A body over a route's own `maxBodyBytes`, or over the request mapping limit, now answers 413 Problem Details `payload-too-large` ("The request body exceeds the N-byte limit.") like the server limit (D6), instead of 422 `validation` with a `body-too-large` issue. An `OPTIONS` request that is not a CORS preflight, on a path that has routes, now answers 204 with an empty body and `Allow` listing the path's methods plus `OPTIONS` (and `HEAD` where `GET` exists), instead of 405. A path without routes still answers 404, and a route that declares its own `OPTIONS` handler is unchanged. The `Allow` header of a 405 now also lists `OPTIONS`. The remaining Problem Details bodies also carry `requestId`: the 413 `payload-too-large` of the server body limit and the 500 sent when a route's `response` option throws. `ResponseMappingOptions` gains `requestId`, and the generated OpenAPI Problem schema declares `requestId` next to `traceId`.
- the generated OpenAPI document now declares the Problem Details responses the server sends for each operation. A route with an access rule declares 401 and 403 (route authentication alone declares 401), an operation that reads input declares 422, one that can have a request body also declares 413 `payload-too-large`, a rate-limited route declares 429 with the rate limit headers, and every operation that runs a function declares 500. An operation that reads no input declares no 422, and one without a request body declares no 413. A response the route declares itself replaces the generated one, and raw handlers keep their single `default` response. The responses refer to one shared `Problem` schema in `components.schemas` instead of repeating it, so a client generated from the document sees a new `Problem` component and `allOf` for the narrowed validation, oversize and rate limit bodies. `OpenApiDocument.components.securitySchemes` is now optional and `components.schemas` is added; `problemSchema` and `PROBLEM_SCHEMA` are exported from `relkit/openapi`.
- `relkit dev` prints the cause of a 500 in the terminal, now that it is no longer in the response body. The generated development server sends the framework's HTTP error log to the terminal: the line after `GET /path → 500` is the redacted cause (`Error: <message>`, with bound query parameters masked) followed by the request and trace IDs; `--verbose` adds the stack. The framework's `Execution operation failed` record for the same failure stays out of the terminal outside `--verbose`. Production output is unchanged: these records go to the observability sink only.
- A file that does not parse is reported by `relkit dev` and `relkit check` at the parse error's own line and column, with the parser's message (`Unexpected =` on Bun, `Unexpected "="` on Node) and further errors listed briefly after it, instead of at line 1 with `2 errors building <absolute path>`. On Bun, `relkit check` no longer waits for the evaluator's 10-second timeout when more than one file imports the broken one.
- The Inspector's history store answers the new request filters of history queries, `status` (exact or class such as `5xx`), `method`, `path` (prefix) and `errorId`, with the same results as the application's own query, and returns `total`, the number of matching records across all pages, when a query asks for `count`.
- The Bun runtime adapter (the server of `relkit start` and of the `relkit dev` worker) never serves Bun's development error page, whatever `NODE_ENV` says: a failure outside the application's own error mapping answers a `500` Problem `internal-error` without paths or source. A `Host` that is not a host with an optional port answers a bare `400`, as on Node, instead of a `500`; a request without `Host` (HTTP/1.0) is served. A Problem from an endpoint under `/_relkit/` (for example `404` for an unknown path such as `/_relkit/v1/nope`) now names the same `requestId` as its `x-request-id` header.
- A read that rejects after its caller aborted no longer surfaces as an unhandled rejection. When the abort had already happened, the abort helper returned its own rejection and left the abandoned read's rejection without a handler; on Node an unhandled rejection can end the process.
- `RuntimeSpawnOptions` of the runtime adapter (`relkit/runtime`) gains `processGroup`: on POSIX the child starts as the leader of its own process group, so `process.kill(-pid, signal)` reaches the child and everything it started. Bun and Node implement it with `detached`; Windows ignores it.
- A generated server now binds each bucket's declared `maxObjectBytes` and `allowedContentTypes` from the application graph to the bucket clients it builds, for function invocations, tasks and the application handle, so a disallowed type or size is refused before signing an upload URL or storing an object with any provider, including `@relkit/s3`.
- `relkit dev` rebuilds only when a file's content changed. The operating system also reports files that were read or copied without a change, and cloning the project folder on macOS (as Finder's Duplicate and `cp -c -R` do) made a running server rebuild once for each source file, more than a hundred times over several minutes with nothing different in any file. The watcher now compares each reported file with what it saw at the last decision (its size and a hash of its content, or its size and modification time for a file over 4 MiB), and skips the rebuild when nothing differs. Edits, deleted files and new files still rebuild. The 75 ms quiet window also gathers the events that arrive during it into one rebuild, as intended; it used to start a separate rebuild for each.
- The in-process HTTP client of `createTestApplication` decides function `access` rules as the served application does: the caller is the request's session with roles and permissions from the Better Auth organization plugin, a rule's roles and permissions are decided before input is validated, and the built-in failures answer `401 unauthenticated` and `403 access-denied` instead of `500`. `invokeFunction` and `runtime.invoke` accept an explicit `principal` for testing a protected function directly. A bucket's declared `maxObjectBytes` and `allowedContentTypes` now hold for every bucket provider the test application wires, including a replacement provider, as they do in the generated server.
- The `relkit dev` proxy no longer answers a bare `400` to the request that follows an early rejection on the same connection. Bun's fetch kept the connection to the worker in its pool after the worker answered before the request body was sent, so the worker read the next request as the rest of that body; the proxy now never reuses a connection that carried a request body, tells the client to close when the worker answered before the client's body ended, and forwards the client's `Content-Length` so the worker applies its body limit as in production. The proxy also forwards request bodies on Node, which refused them before.
- The R2 bucket provider takes the bucket's `maxObjectBytes` and `allowedContentTypes`, applies them to `put`, and binds a declared content type and exact length into signed upload URLs, as the S3 provider does. The R2 binding provider takes no limits yet.
- The inspection API now passes a channel's declared `params`, `replay` and `presence`, and an agent's `modelSource` and `instructions`, through the graph projection, so the Inspector shows a channel's partition parameters and replay window instead of "Not declared" and "live only". A rejected Inspector action now carries the application's answer under `cause`: the HTTP status it would have sent and its safe error code (`{ "status": 401, "code": "unauthenticated" }` for a function whose access rule needs a session, a declared error's id and status, or `validation` with the invalid field paths), never the message or data. The action's own status and `error` code are unchanged. Every graph and runtime collection page of the inspection API now carries `total`, the number of records matching its filters, so the Inspector can say "20 of 23". The runtime events page passes through a delivery `total` and per-state `counts` when the event provider reports them. `createInspectorEventActions` (from `relkit/inspector-api`) provides the Inspector's event publish, replay, status, retry and cancel for a development server: publish goes through the application's own event client with the event's declared schema, so an invalid payload is refused (`422`, `cause.issues` naming the fields); replay uses the provider's `replay` when it has one and otherwise publishes the stored payload of the publication again; a provider without the operation answers `RELKIT_INSPECTOR_ACTION_UNSUPPORTED` (`501`). Inspector action errors whose code names a validation now answer `422` and unsupported ones `501`. The local event provider's query accepts `publicationId` and then returns that publication's stored `payload`. Observed edges in the inspection API now keep `count`, `firstSeenAt` and `lastSeenAt` when the runtime reports them. The agent workflow and executions inspection routes (`/_relkit/v1/agents/:agentId/workflow`, `/_relkit/v1/runtime/agents/:agentId/executions`) no longer answer callers without credentials: they answer the development inspection session that a generated server registers under `Symbol.for("relkit.inspection.authorize")`, or explicitly configured internal credentials, and otherwise answer 404 (401 for a failed check). Other internal endpoints and the development API documentation are unchanged. An Inspector waiting for a development session no longer logs `connection.path.stat … ENOENT` as a failed operation every second while the project has no `.relkit/connections` directory; a missing path is absence, and other failures are still logged. The history routes of the inspection API (`/requests`, `/logs`, `/traces`) now pass the `status`, `method`, `path`, `errorId` and `count` filters to the observability store, and the runtime telemetry counters include `exportCapacityRejections`.
- When the frozen lockfile check fails, `relkit doctor` says why. Under `✗ lockfile: Frozen lockfile consistency check failed.` it prints the package manager's own first lines, such as npm's `Missing: left-pad@1.3.0 from lock file`, without npm's usage text, and `relkit doctor --json` carries the same lines in `checks[].details.reason` next to the `command` that was run. Credentials, registry logins and your project path in that output are masked.
- The Inspector and `relkit mcp`'s `graph` tool read the whole application graph again. Since the application-port graph probe was reduced to its activation witness, `GET /_relkit/v1/graph` through the development bridge answered identity only, and every Inspector page failed with "This page couldn't load". The generated development server now answers that probe with the Inspector API's graph projection when the request carries the development inspection session (which only the bridge adds); any other caller, including one with an application session or a wrong session token, still gets identity only. The Inspector shows its not-available state when an application answers without a graph instead of failing the whole page, and a provider's page shows its failed state instead of loading forever.
- invoking a function, connecting to a channel and sending a route request show the application's answer in words, including that Inspector actions run without a user session when the application refuses a call for that reason, and the channel parameters start from the declared ones. Event publish and replay check the payload against the event's schema, ask for confirmation, and answer beside the control, including a provider that cannot retry a delivery. Event pages and lists state their totals (100+ with a way to load more, 20 of 23), and publication and delivery rows show their time, payload preview and trace. The Errors page shows how many retained requests ended with each declared error and the unexpected failures; the Routes page lists the authentication mount, health probe and RPC as system routes. The Jobs pages say that no jobs are declared instead of reporting an unavailable service, and empty resource pages tell none declared from no match. Bucket objects show their content type and modified time and flag a type that contradicts the key, PDF previews show their metadata with a download, Providers word the source as provenance and show the reported health, function forms label fields with defaults as optional, and the Env page no longer overflows at 900 px.
- `relkit dev` reports a type error saved while the type checker is still on its first pass. The checker reads the project before it watches it, so such a file was checked as it was before the save and never again: the terminal kept saying "No type errors". The first pass is now discarded and the checker started again (at most twice) when a source file was saved after it started.
- Every Problem Details response carries `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`, including the ones the framework sends before a route runs: the 404 of an unmatched path, the 405 of a wrong method and the 413 of a body over the limit. `problemResponse` sets both headers, so a Problem built anywhere in the framework has them and a response that sets its own `Cache-Control` keeps it.
- The `relkit dev` front, on Bun and on Node: - A missing or malformed `Host` no longer answers Bun's `500` error page with the CLI's source paths: a `Host` that is not a host with an optional port answers a bare `400`, and a request without `Host` (HTTP/1.0) or with an empty one is served with the front's own address. No failure of the front serves Bun's error page; it answers a `500` Problem `internal-error`. - The path the front checks is the path it forwards: a `Host` carrying a path no longer changes the route, and a path starting with `//` answers `404` on both runtimes instead of reaching the application (and its inspection endpoints) on Bun. - A `GET`, `HEAD` or `OPTIONS` that carries a body no longer makes the next request, from any client, answer `400` or nothing on Bun: a `Content-Length` is forwarded only with its body. - The `404` for a blocked inspection path names the same `requestId` as its `x-request-id` header. - A client that disconnects before reading the body no longer prints `Error: aborted` in the terminal. When the new version stops before it is ready after reporting a coded startup failure (such as `RELKIT_PROVIDER_CONFIGURATION_INVALID` with `--local off` and a local-only binding), `relkit dev` now ends with that code, its message and its next step instead of `RELKIT_INTERNAL_ERROR` and a request to report a bug. The command then exits with status 1, whatever exit code the new version itself ended with.
- `relkit dev` bounds the baseline it reads to tell a real edit from an event without a change: at most 20,000 entries and 256 MiB per watched directory, so a project root that holds far more than source no longer delays the start. A file outside the baseline, or created later, counts as changed the first time it is seen and is compared from then on.
- An answer that leaves its request body unread waits at most 500 ms for the rest of that body. A client that stalls or trickles its upload now gets the answer and a closing connection, not a response held until the upload ends.
- The Inspector's graph carries each function's access rule (its roles, its permissions, and whether a predicate decides), so the architecture view counts a route whose function is guarded as protected. Route groups no longer read "all public"; without a reported rule they read "no access rule reported".
- `SIGTERM` sent to `relkit dev` alone now ends the process within a few seconds and leaves nothing behind. The type-check watch runs the project's compiler behind a JavaScript launcher (the `typescript` 7 launcher on Bun and on Node before 22.15, `tsgo`, or any launcher script) that starts the native compiler as its own child and does not forward signals; stopping only the launcher left the native compiler running with the output pipe open, so the CLI logged `dev.stopped` but never exited. The watch now starts in its own process group, a stop signals the whole group, escalates to `SIGKILL` after one second, and cancels the output reader. Ctrl+C in a terminal behaves as before. On Windows, which has no process groups, only the launcher is signalled.
- The Inspector counts and names the records it collected but could not store, instead of reporting that nothing was lost. It still acknowledges a batch to the application only once history holds it, so a batch that could not be stored stays in the application's inspection buffer and is stored when history works again. Two cases lose records, and both now show in `/_relkit/v1/storage` as `recordsLostBeforeHistory.byHistoryStore`, keep `incomplete: true` for the rest of the Inspector's run, and leave a `RELKIT_INSPECTION_INCOMPLETE` diagnostic in history that says how many records and which: a record the history store refuses (the rest of its batch is now stored one record at a time instead of failing with it), and a batch whose application session ended before history could store it.
- `relkit dev` reports a save that does not parse, or a module that throws while it loads, at once instead of after a 10-second timeout, and a fix saved meanwhile is live right after. The failure is one error block: `Reload failed; previous version is still serving` followed by the cause. When the new process exits while it starts (a configuration or module that fails only in the served process), the block shows what the process wrote, with the file and line, instead of the startup lines as warnings and `RELKIT_CANDIDATE_HEALTH_TIMEOUT`. The `dev.generation.active`, `dev.generation.swapped` and `dev.generation.failed` events carry `runId`, one identifier per `relkit dev` process, and `reason`: `start` for the first generation of a run, `reload` for handlers swapped in the serving process, `restart` for a new process. A generation history can now tell a restart of the command from a reload. A development generation started with a custom candidate host (`candidateHostname`) now binds that host: the host the supervisor allocated the port on is passed to the generated server.
- a 404 from the RPC endpoint (`relkit.rpc`), such as a call to a procedure it does not serve, is recorded with the outcome `refused` instead of `declared-error`: the framework refused it, and no application declared that error.
- New diagnostic code `RELKIT_EVALUATOR_BUN_RUNTIME_REQUIRED` for an application import of a Bun-only module evaluated on Node. The next step of `RELKIT_PROVIDER_RELEASE_SOURCE_REQUIRED` now names a connected adapter with binding values or an infrastructure source, and `RELKIT_GRAPH_NOT_FOUND` explains that the graph is written only when `relkit check` passes.
- The Inspector's pages refuse a request that is not addressed to the Inspector's own address, for reads as well as actions, so a page served from another name that resolves to this machine (DNS rebinding) cannot read inspection data or run an action. The accepted addresses are `127.0.0.1`, `localhost`, `[::1]` and the configured host, on the Inspector's port; with a wildcard bind (`0.0.0.0` or `::`) any IP address is accepted. An Inspector opened through another DNS name is refused: bind it to that name with `--hostname`. An application outage reads "The application is unreachable. Retained history is intact." and no longer "history degraded". The route composer no longer offers cookie fields, which a browser never sent, and composer and action results say that they ran without a user session.
- the API reference for the mounted Better Auth endpoints is true to what they send. Better Auth's `nullable: true` (OpenAPI 3.0) becomes `type: [..., "null"]` (OpenAPI 3.1), so the `image` of a new user validates as `null`; `POST /organization/delete` describes the organization it returns, `POST /organization/has-permission` allows `error: null`, and `check-slug`, `list-invitations` and `list-members` declare their 200 answers. Every endpoint that takes a body also declares 413 (`payload-too-large`, from the server's body limit) and 415 (Content-Type not accepted). The new `BetterAuthProblem` component holds the Problem Details schema of the 413. Differences that remain are listed on the Better Auth documentation page.
- The Inspector refuses a state-changing request that the browser marks as sent by another site (`Sec-Fetch-Site: cross-site` or `same-site`) before anything reaches the application. What it forwards to the application is its own call: the browser's `Origin`, `Referer`, `Sec-Fetch-*` and proxy forwarding headers are dropped, and so are the browser's cookies, which for the Inspector's host also include the application's, so invoking a function, publishing or replaying an event and sending a route request run without a user session, as documented. An `Authorization` header typed in the route composer is still sent. History status says what is true. During an outage of the application, retained history is `ready` and the new `collection` field is `application-unreachable`, with the failure in the new `applicationError` field; `state: degraded` and `error` now mean that history itself is unavailable (`collection: history-unavailable`). A tool with no development session and no lost record no longer reports history as `incomplete`; a loss reported once stays reported for that session.
- `relkit` now depends on `@hono/node-server` 2.1.6 instead of 2.1.5, so a fresh `npm install` no longer reports the two moderate advisories that 2.1.5 carries (an unhandled `ECONNRESET` on the socket during a WebSocket upgrade, and a backslash in the request path parsed as a path separator), which `npm audit` attributed to every `@relkit/*` package. A request whose path contains a raw backslash is now answered 400 by the Node server; a percent-encoded backslash (`%5C`) is still accepted. Projects with authentication get Better Auth 1.7.7, which closes the Better Auth advisories `npm audit` reported for 1.7.1; see the Better Auth changeset.
- a WebSocket upgrade to `/_relkit/v1/rpc` from a refused origin is answered with 403 and the `origin-denied` Problem, as an HTTP request from that origin is, instead of a 500 `internal-error`. Through `relkit dev`, a refused upgrade is no longer a bare `502 Bad Gateway`: on Node the development proxy repeats the application's status, content type and request id; on Bun, whose WebSocket client does not report the status, the proxy refuses a foreign or opaque `Origin` itself with 403 `origin-denied` and answers any other refusal with a 502 Problem, both with an `x-request-id`. On Node a refused upgrade carries no body, because Hono's Node server sends only the status and headers of a refused upgrade.
- On Node, a request whose client sent no body (no `Transfer-Encoding`, and no `Content-Length` or `Content-Length: 0`) now reaches route and mounted handlers with `request.body === null`, as on Bun. The Node listener used to give every request other than `GET` and `HEAD` an empty body stream, so Better Auth's sign-out (a `POST` without a body or content type) answered 415 `UNSUPPORTED_MEDIA_TYPE` under `relkit start` and `relkit dev` on Node. The request keeps its method, URL, headers and signal.
- a channel guard that calls `getRelkit()` (for example to look a membership up in the database) refused a signed-in user over the WebSocket transport with `NOT_FOUND`, on Node and on Bun, while the same user was served over the HTTP stream. Socket messages arrived outside the asynchronous context of the upgrade request, so `getRelkit()` threw and the guard's failure was concealed as a refusal. Each message now runs in the upgrade request's context.
- An answer sent before the request body was read (origin denial, body limit, unknown route, wrong method, a route that requires a session, not ready) no longer leaves the connection in an unknown state: the server reads and discards the rest of the body up to `server.maxBodyBytes`, and answers with `Connection: close` when the body is larger than that or its size cannot be bounded. `server.maxBodyBytes` now applies to the bytes of every request, not only to a declared `Content-Length`: a body sent without one is read up to the limit before any route or mounted handler sees it, so a chunked request to the mounted Better Auth handler can no longer exceed it. An oversize body now answers `413` with the Problem Details code `payload-too-large` whether its length was declared or it was streamed, in development and in production; a streamed oversize body used to answer `422`. Responses under `/_relkit/` (health, readiness and the other control-plane endpoints) now carry `x-request-id` like every other response; they are still not recorded as application requests.
- On Node, `relkit db migrate`, `relkit env check` and `relkit env list` now read the application's environment files (`.env`, `.env.<mode>`, `.env.local` outside test, `.env.<mode>.local`), as Bun already did. A value already set in the process environment takes precedence over the files. `relkit db migrate` on Node also finds an installed drizzle-kit that does not export its `package.json`, so PostgreSQL and MySQL migrations run through `npm run`. When the Drizzle configuration fails to load, `relkit db migrate` now shows the configuration's own message, such as `Set DATABASE_URL to the database you intend to migrate`, with credentials in URLs and `password=`-style values masked. A configuration that imports a package that is not installed is reported as a missing dependency instead. `relkit db migrate` now says what it did: `Applied 2 migrations; the database is up to date.` or `Database is up to date: no migrations were pending.`. The JSON result gains `history` (migrations in the history folder) and, when the CLI could read the migration log, `applied`. SQLite always reports the count; PostgreSQL reports it when the application uses `pg`, and otherwise says the database matches the history without claiming work. The message for a missing migration history names the project's package manager (`npm run db:generate`, `pnpm run db:generate`), and `relkit db migrate --help` lists the environment files the configuration reads.
- a channel stream whose client went away while the server waited for the next event failed with `HttpBoundaryError realtime.wait` and was logged at error level as "Execution operation failed" (`operation=realtime.observe`), although its request was recorded as cancelled. The stream now ends when its caller's signal aborts during the wait, and no error is logged.
- A realtime subscription whose identity scope or session epoch does not match the session now answers `409` with `IDENTITY_PRECONDITION_FAILED` before any stream is opened; it used to open the stream and fail inside it, which a client saw as `500`. Channel authorization is unchanged: a channel the caller cannot read still ends the stream with the concealed `NOT_FOUND`. `createWriteUrl(key, { contentType, contentLength })` now takes the upload's content type and length, both optional; calls without them are unchanged. A declared type outside the bucket's `allowedContentTypes`, or a length above `maxObjectBytes`, fails with the bucket policy error (`RELKIT_BUCKET_POLICY_INVALID`) before a URL is signed, and the provider binds the type and the exact length into the URL so storage rejects any other upload. Without a declaration the URL binds neither and the bucket's limits are not enforced on that upload. The new `BucketPolicyError` (exported from `relkit/buckets`) is the policy error of every provider; the local provider's `LocalBucketPolicyError` now extends it. A bucket client given a `policy` applies it to `put` and `createWriteUrl` before calling the provider. The bucket clients a running application builds (in function contexts and on the application handle) now receive the bucket's declared `maxObjectBytes` and `allowedContentTypes`, from the authored `defineBucket` descriptor or, for a bare reference and in a generated server, from the bucket's node in the application graph (bound to its source with the new `bindBucketPolicy` from `relkit/engine`), so the limits hold with `@relkit/s3` and every other provider, not only the local one.
- Added: the request outcome `refused`, for the framework's own early answers. A path no route matches (404), a method the path does not accept (405) and a body over `maxBodyBytes` (413) are recorded as `refused` instead of `declared-error` or `validation-error`, so the outcome filter separates them from errors an application declared. `REQUEST_OUTCOMES` and `RequestOutcome` include the new value; code that switches over every outcome needs a case for it. A route's own 404 keeps `declared-error`.
- `relkit dev` on Node serves the Inspector's actions: invoking a function, publishing or replaying an event and a `POST` from the route composer were refused with 403 `origin-denied`, because the inspection bridge forwarded them with Node's `fetch`, which drops the development listener's `Host`, so the application compared their `Origin` with its private worker port. They now go through the same Host-preserving client as other development traffic. Bun was not affected.

- `relkit dev` run by Node now serves a same-origin `POST`, `PUT`, `PATCH` or `DELETE`. Node's `fetch` replaces the `Host` header the development proxy forwards with the worker's private address, so the worker judged every browser `Origin` as foreign and answered 403 `origin-denied`. On Node the proxy now forwards over `node:http`, which keeps `Host`, as Bun's `fetch` already did. Cross-origin requests are still denied, and forwarding headers sent by the client are not trusted. `relkit dev` run by Node now accepts a same-origin WebSocket, so realtime channels and the RPC socket work from a browser. Node's `WebSocket` client also replaced `Host` on the proxy's upstream socket, so the worker refused every browser socket and the development server answered 502. On Node the proxy now opens that socket with `ws`, which keeps `Host` and forwards the browser's cookies and `Origin`; Bun keeps its own client. Cross-origin sockets are still refused. The development proxy no longer invents a request body: a request whose client sent none (no `Transfer-Encoding`, and no `Content-Length` or `Content-Length: 0`) is forwarded without one, where on Node it used to be forwarded as an empty chunked body, so Better Auth's sign-out answered 415 under `relkit dev` on Node. `relkit dev` run by Node now delivers the worker's answer to a request whose body the worker refused early, such as a 413 for a body over `server.maxBodyBytes`. The proxy's Node client waited for the whole body to be sent first, so a large body could hang until the client gave up, and a write error before the answer was read turned it into the proxy's own `500`. The answer is now delivered once the worker ends its side or still holds the body back after a short grace; the rest of the body is not sent and the client's connection is closed after the answer. The proxy also stops forwarding the worker's connection headers (`Connection`, `Keep-Alive`, `Transfer-Encoding`), so a client's `Connection: close` is honoured.
